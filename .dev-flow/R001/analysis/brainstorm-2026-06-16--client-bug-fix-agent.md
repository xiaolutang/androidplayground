# 客户端 Bug 修复 Agent 设计

## 结论
- **要做什么**：客户端 bug **自动修复** agent，覆盖 Flutter 为主 + Android 原生辅助；自动修复是核心目标，不做"只诊断不修复"的退化版
- **不做什么**：物理边界外问题（真机依赖的性能/厂商 ROM/硬件）——除非后续补真机矩阵；不做 Flutter integration_test 自动生成
- **关键约束**：模拟器起步；视觉决策 + ADB 操控；分层动态化，能力边界随基础设施补齐而下移
- **核心场景**：bug 上报 → 分层分流 → Tier 1 自动修复闭环 / Tier 2 草稿 PR / Tier 3-4 缺口诊断与回流
- **核心机制**：**四组件架构** —— Playbook（方法论）+ Knowledge Base（经验）+ Information Sufficiency Model（bug 级信息补全）+ Capability Gap Tracker（agent 能力级缺口管理）
- **待确认**：触发源平台（Bugly / Crashlytics / Sentry / 自建）

## 核心设计抽象：四组件

**Playbook（方法论）**：五类症状各对应独立 Playbook —— 空白 / Loading / 点击无响应 / 数据错 / 崩溃
每个 Playbook 含 5 字段：判定信号、锚点来源、探测动作集、根因假设空间、诱发动作集
- 崩溃型：被动等信号（三级分级 + 步数兜底）
- 症状型：主动探测 + 锚点对照 + 辅助信号（logcat/抓包/Widget tree）+ 主动诱发

**Knowledge Base（经验）**：三层沉淀，让 agent 越用越准
- 单 bug 内：排查轨迹 Trajectory —— 假设树而非线性 log，支持回溯
- 跨 bug：失败假设库 + 高频命中根因
- 组织级：症状 → 根因概率分布

**Information Sufficiency Model（bug 级信息补全）**：处理单 bug 信息不全
- 信息缺口分类 A/B/C/D + 四类应对（主动探测 > 结构化追问 > 假设驱动 > 降级）
- 关键洞察：信息是排查的副产品，不是前置条件

**Capability Gap Tracker（agent 能力级缺口管理）**：让 agent 越用越准的核心机制
- 四类缺口：**信息缺口**（补上下文文档）/ **基础设施缺口**（补工具测试真机）/ **模式缺口**（人修一次沉淀进 KB）/ **模型能力缺口**（标记等升级）
- 每个"修不了"的 bug 不再是失败，而是"能力升级 TODO"
- 补齐后 bug 自动回流，agent 重试 → Tier 升级

## 自动修复的动态分层（关键认知修正）

**三维可修复性标准**（不是 bug 类型，是这三个维度的组合）：
- **信息完备度**：修这个 bug 需要的信息能不能完整给到 agent
- **验证可行性**：修完能否快速、确定性地验证（有测试？能复现？能跑回归？）
- **模式化程度**：这类 bug 的修法有没有规律（空指针模板 vs 业务重设计）

**四层动态分层**：

| Tier | 特征 | agent 动作 | 例子 |
|------|------|----------|------|
| **Tier 1** | 三维都高 | 复现 → 修 → 验证 → 提 PR，人审核 | Flutter Widget build 空指针 |
| **Tier 2** | 部分维度中等 | 出 patch 草稿 + 理由，draft PR | 状态机转移条件错 |
| **Tier 3** | 多维偏低 | 不碰代码，出诊断报告 + 缺口诊断 | 跨模块业务逻辑错 |
| **Tier 4** | 物理边界外 | 拒绝处理，记录缺口 | 真机 ROM 相关崩溃 |

**分层是动态的**：随基础设施补齐整体下移；下移驱动力来自 Capability Gap Tracker。

## 自动修复的关键设计

- **修复输入**（5 类线索）：位置 / 根因解释 / 上下文代码 / 预期行为 / 历史相似修法
- **修复机制**（按可解决性优先级）：**模板修复**（模式化）→ **LLM 生成 patch**（覆盖模板外）→ **KB 历史校准**（相似 commit 套用）
- **修复验证**（必过三关）：复现序列回归（bug 没了）+ 既有测试套件全过 + 静态检查通过
- **修复产出**：按 Tier 分流 —— Tier 1 直接 PR / Tier 2 draft PR / Tier 3-4 不产出代码只产出诊断与缺口
- **人的位置**：审核合并者 + 缺口补齐者 + 卡住干预者；**人不再是修复者**

## 关键决策
- 锚点方案：**D（关键页面截图库 + bug 描述文字预期组合）**
- 操控路线：**视觉决策主路径 + ADB 辅助**（不做 integration_test 自动生成）
- **MVP = Tier 1 端到端闭环 + Capability Gap Tracker 同步建设**，让 Tier 边界随时间下移
- C 产物字段：复现操作序列、信号配置、根因定位、相似历史 issue、假设树 trajectory、**能力缺口描述**

## 关键讨论（设计演进史）
1. 不同症状不同复现思路 → 催生 **Playbook** 抽象
2. 症状型 bug（空白页）暴露"被动等信号"失效 → 引入主动探测
3. 排查方向可能走错 → 催生 **Knowledge Base**（trajectory / 负向知识 / 根因模式三层）
4. 信息不全 → 催生 **Information Sufficiency Model**
5. 用户校正"想要自动修复而非诊断" → **自动修复从 MVP 外移到核心**，引入修复置信度评估与分层
6. 用户挑战"为什么复杂业务/性能/ROM 不能修" → 推翻静态分层，提出**三维可修复性标准 + 动态分层**
7. 用户挑战"一杆子打死 agent 怎么进步" → 催生 **Capability Gap Tracker**，把"修不了"转化为"能力升级 TODO"
