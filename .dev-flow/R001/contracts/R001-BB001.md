## 任务边界

### 做什么（IN scope）

1. **新建 `agent/assessment/info_sufficiency_evaluator.py`**（当前为空文件，待实现）：信息完备度评估器（ISM），输入 BugReport + KB 检索结果，输出 `ISMResult`（level / score / gaps / clarify_questions / degraded / reasoning）。

2. **三档分级**（ISMLevel 枚举）：
   - `SUFFICIENT`（score >= 0.8）：信息完备，可进 BB002 症状分类。
   - `BORDERLINE`（0.5 <= score < 0.8）：信息临界，触发追问子回路（`clarify_questions` 非空）。
   - `INSUFFICIENT`（score < 0.5）：信息不足，降级（`degraded=True`）。

3. **临界追问**（assessing 子回路）：`BORDERLINE` → `clarify_questions` 为非空 `list[str]`，由 KB 检索结果（BF005 `RetrievalResult`）派生候选 gaps（A/B/C/D 类），供 FB004 结构化追问消费。追问 loop 不新增 BugReport 状态——`status` 保持在 `assessing`，置 `clarify_requested=true` 由 Orchestrator（ORB01）负责。

4. **不足降级**：`INSUFFICIENT` → `degraded=True`，Orchestrator 据此转 Tier3/4 缺口诊断路径。

5. **调 LLMGateway**（INF04）：`prompt_type="symptom_classify"`（text 通道，经 `_PROMPT_TYPE_TO_CHANNEL` 路由到 glm-5.1）。system prompt 指示 LLM 作为 bug 分诊专家评估信息完备度；user prompt 包含 BugReport 摘要 + KB gaps 候选。LLM 返回 JSON，解析为 `ISMResult`。

6. **追问候选从 KB 派生**（BF005）：调用方传入 `kb_context: RetrievalResult | None`，ISM 从中提取候选 gaps 类型（A=复现信息 / B=环境信息 / C=日志信息 / D=预期信息），构造 `clarify_questions`。

7. **ISMResult dataclass**：`level: str`（ISMLevel 枚举值）/ `score: float`（0.0-1.0）/ `gaps: list[str]`（A/B/C/D 分类标签）/ `clarify_questions: list[str]` / `degraded: bool` / `reasoning: str`（LLM 推理摘要）。

8. **LLM 失败降级**：LLMGateway 抛 `LLMError`（超时/超限/解析失败耗尽）时，ISM 返回 `ISMResult(level=INSUFFICIENT, score=0.0, gaps=[], clarify_questions=[], degraded=True, reasoning="LLM failure: ...")`，不向调用方抛异常。

9. **单元测试**：`tests/unit/assessment/test_info_sufficiency_evaluator.py`，全 mock（LLMGateway 用 `FakeLLMGateway`，KB 用 mock `RetrievalResult`）。

### 不做什么（OUT of scope）

- **不实现 Orchestrator 子回路**（ORB01 负责）：ISM 只输出 `ISMResult`，不负责更新 `BugReport.clarify_requested` / `BugReport.status` / `BugReport.completeness_score` / `BugReport.gaps` 字段。Orchestrator 消费 `ISMResult` 后自行决定状态迁移与持久化。
- **不实现 clarify_questions 的用户交互**（FF001 / FB004 负责）：ISM 只产出追问候选列表，不负责 `/clarify-options` / `/clarify` API 或前端表单。
- **不实现 BugReport 的持久化**：ISM 是纯计算函数，输入 `BugReport`（ORM 对象或 dict）+ `kb_context`，输出 `ISMResult`（内存对象）。不碰 DB。
- **不实现 KB 检索**（BF005 负责）：ISM 消费 `RetrievalResult`，不自行调 `KBRetriever.retrieve`。调用方（Orchestrator）先检索再传入。
- **不实现症状分类**（BB002 负责）：ISM 评估信息完备度，不判断 crash/blank/loading 等症状类型。
- **不做异步接口**：ISM evaluator 为同步函数（LLMGateway.complete 是 async，ISM 内部 `asyncio.run` 或由调用方 await——见 Q6）。

## 验收标准（可测试）

### AC-1：评估接口

- **断言**：`InfoSufficiencyEvaluator(llm_gateway).evaluate(bug_report, kb_context=kb_result)` 返回 `ISMResult` 实例。
- **断言**：`ISMResult` 字段：`level: str`（值为 `"sufficient"` / `"borderline"` / `"insufficient"`）/ `score: float`（0.0-1.0）/ `gaps: list[str]`（元素为 `"A"` / `"B"` / `"C"` / `"D"`）/ `clarify_questions: list[str]` / `degraded: bool` / `reasoning: str`。
- **断言**：`bug_report` 参数接受 `BugReport` ORM 对象或 dict（duck typing：只要有 `raw_report` / `version_code` / `symptom_type` 等属性即可）。
- **断言**：`kb_context` 参数接受 `RetrievalResult` 或 `None`（None 时 gaps 候选为空，但仍交 LLM 评估）。

### AC-2：三档分级阈值

- **断言**：LLM 返回 `score=0.85` → `level="sufficient"`（score >= `ISM_THRESHOLD_SUFFICIENT=0.8`）。
- **断言**：LLM 返回 `score=0.6` → `level="borderline"`（`ISM_THRESHOLD_BORDERLINE=0.5` <= score < 0.8）。
- **断言**：LLM 返回 `score=0.3` → `level="insufficient"`（score < 0.5）。
- **断言**：阈值边界：score=0.8 → sufficient（>=）；score=0.5 → borderline（>=）；score=0.79 → borderline；score=0.49 → insufficient。
- **断言**：level 由 ISM 根据 score 自行判定（不信任 LLM 返回的 level 字段，ISM 用 score + 阈值重新计算 level，防止 LLM 幻觉）。

### AC-3：临界追问

- **断言**：`level="borderline"` → `clarify_questions` 为非空 `list[str]`（至少 1 条）。
- **断言**：`level="sufficient"` → `clarify_questions` 为空 `list`（`[]`）。
- **断言**：`level="insufficient"` → `clarify_questions` 为空 `list`（`[]`，不足直接降级，不追问）。
- **断言**：`clarify_questions` 内容由 KB gaps 候选派生（kb_context 提供候选时，追问问题对应 A/B/C/D 类别）。

### AC-4：不足降级

- **断言**：`level="insufficient"` → `degraded=True`。
- **断言**：`level="sufficient"` → `degraded=False`。
- **断言**：`level="borderline"` → `degraded=False`（临界不降级，走追问子回路）。

### AC-5：LLMGateway 调用

- **断言**：内部调 `llm_gateway.complete(prompt_type="symptom_classify", messages=[...])`（text 通道，路由到 glm-5.1）。
- **断言**：messages 构造：system role 含 "bug 分诊专家" / "信息完备度" 关键词；user role 含 BugReport 摘要（version_code / symptom_type / raw_report 摘要）+ KB gaps 候选列表。
- **断言**：LLM 返回 JSON 字符串解析成功：`json.loads(response.content)` 提取 `level` / `score` / `gaps` / `clarify_questions` / `reasoning`。
- **断言**：LLM 返回非法 JSON（或缺失字段）时，ISM 用 score=0.0 兜底（insufficient），不抛异常。

### AC-6：KB 派生追问

- **断言**：`kb_context` 提供 entries（含 `KBEntry`）时，ISM 从 entries 的 `layer` / `symptom_type` / metadata 派生 gaps 候选（A/B/C/D 分类标签）。
- **断言**：`kb_context=None` 时，gaps 候选为空 `[]`，LLM 自行评估（不阻塞）。
- **断言**：`kb_context.degraded=True`（冷启动/低相似度）时，gaps 候选仍尽力提取（degraded 不等于空，只是检索质量低）。

### AC-7：gaps 分类

- **断言**：`gaps` 元素为 `"A"` / `"B"` / `"C"` / `"D"` 中的一个或多个。
- **断言**：分类语义：A=复现信息缺失（无步骤/无触发条件）/ B=环境信息缺失（无版本/无设备型号）/ C=日志信息缺失（无堆栈/无 logcat）/ D=预期信息缺失（无期望行为描述）。
- **断言**：gaps 分类逻辑：ISM 从 BugReport 字段检查（raw_report 有无 reproduction_steps → A；version_code/device_model → B；stacktrace/logs → C；expected_behavior → D），结合 LLM 判断。

### AC-8：LLM 失败降级

- **断言**：`FakeLLMGateway` 队列空（抛 `LLMError`）→ `ISMResult(level="insufficient", score=0.0, gaps=[], clarify_questions=[], degraded=True, reasoning 含 "LLM failure")`。
- **断言**：LLM 返回空字符串（`content=""`）→ 同上降级（`FakeLLMGateway` 队列返回空字符串模拟 INF04 的 empty content 场景，但 INF04 本身已对 empty content 做了重试+抛 LLMError，所以 ISM 收到的是 `LLMError`）。
- **断言**：ISM 不向调用方抛 `LLMError`（内部 catch，降级为 insufficient）。

## 风险与降级

| 风险 | 影响 | 降级 |
|------|------|------|
| LLM 返回 score 与 level 不一致（幻觉） | level 误判，错误路由 | ISM 用 score + 阈值重算 level，不信任 LLM 返回的 level 字段 |
| LLM 返回非法 JSON / 缺字段 | 解析失败 | 兜底 insufficient + degraded=True，不抛异常 |
| LLM 超时/超限（LLMError） | 评估中断 | 内部 catch LLMError，降级 insufficient + degraded=True |
| KB 冷启动（kb_context.degraded=True） | gaps 候选质量低 | 仍尽力提取候选，LLM 自行评估兜底 |
| 阈值需校准（0.8/0.5 为 design 默认） | 误判 sufficient/borderline | 阈值参数化（`ISM_THRESHOLD_SUFFICIENT` / `ISM_THRESHOLD_BORDERLINE`），config 可覆盖，待校准 |

## 实现要点

### Q1：ISMResult dataclass？

```python
@dataclass(frozen=True)
class ISMResult:
    """信息完备度评估结果。

    Attributes:
        level: 评估等级（"sufficient" / "borderline" / "insufficient"）。
        score: 完备度分数（0.0-1.0）。
        gaps: 信息缺口分类列表（元素为 "A" / "B" / "C" / "D"）。
        clarify_questions: 追问问题列表（borderline 时非空）。
        degraded: 是否降级（insufficient 时 True）。
        reasoning: LLM 推理摘要（或降级原因）。
    """
    level: str
    score: float
    gaps: list[str]
    clarify_questions: list[str]
    degraded: bool
    reasoning: str
```

### Q2：ISMLevel 枚举？

```python
class ISMLevel(str, Enum):
    SUFFICIENT = "sufficient"
    BORDERLINE = "borderline"
    INSUFFICIENT = "insufficient"
```

ISM 内部用枚举，输出 `ISMResult.level` 为字符串值（`ISMLevel.SUFFICIENT.value`），便于 JSON 序列化。

### Q3：prompt 模板？

**system**：
```
你是 bug 分诊专家。评估 bug 报告的信息完备度。
根据提供的 bug 报告内容和 KB 检索候选，判断信息是否足够进入自动修复流程。

评估维度（gaps 分类）：
- A: 复现信息（步骤/触发条件）
- B: 环境信息（版本/设备型号/OS）
- C: 日志信息（堆栈/logcat/crash log）
- D: 预期信息（期望行为/实际行为对比）

输出 JSON 格式：
{"level": "sufficient|borderline|insufficient", "score": 0.0-1.0, "gaps": ["A","B"], "clarify_questions": ["..."], "reasoning": "..."}
```

**user**：
```
Bug 报告摘要：
- version_code: {bug_report.version_code}
- symptom_type: {bug_report.symptom_type}
- raw_report: {bug_report.raw_report 摘要}

KB 检索候选 gaps：{从 kb_context 派生的 A/B/C/D 候选列表}
```

### Q4：LLM 输出 JSON？

预期输出：
```json
{
  "level": "borderline",
  "score": 0.6,
  "gaps": ["A", "C"],
  "clarify_questions": ["请提供详细的复现步骤", "请附上崩溃堆栈日志"],
  "reasoning": "缺少复现步骤和堆栈日志，无法自动定位根因"
}
```

ISM 解析后：
- `score` 直接使用（0.0-1.0）。
- `level` **重算**（用 score + 阈值，不信任 LLM 返回值）。
- `gaps` 直接使用（A/B/C/D 标签）。
- `clarify_questions` 直接使用（但仅当重算后 level=borderline 时保留，sufficient/insufficient 时清空）。
- `reasoning` 直接使用。

### Q5：阈值是否可配？

常量定义在模块顶部（或 config，MVP 用常量）：

```python
ISM_THRESHOLD_SUFFICIENT: float = 0.8
ISM_THRESHOLD_BORDERLINE: float = 0.5
```

### Q6：同步还是异步？

LLMGateway.complete 是 `async`。ISM evaluator 的 `evaluate` 方法为 `async def`，调用方（Orchestrator）在 async 上下文中 `await evaluator.evaluate(...)`。单元测试用 `asyncio.run` 或 `pytest-asyncio` 驱动。

### Q7：gaps 候选如何从 KB 派生？

从 `kb_context.entries`（`list[RetrievedEntry]`）提取：
- 每个 `RetrievedEntry.entry`（`KBEntry`）的 `layer` / `symptom_type` / metadata（如有 `gap_hint` 字段）映射到 A/B/C/D 候选。
- MVP 简化：若 `kb_context` 的 entries 覆盖了某 symptom_type 的常见 gaps（如 crash 类常见缺 C 类日志），则加入候选。
- `kb_context=None` 或 entries 为空 → 候选为空，LLM 自行从 BugReport 字段判断 gaps。

### Q8：BugReport dict 输入支持？

ISM 通过 duck typing 访问 BugReport 字段（`.raw_report` / `.version_code` / `.symptom_type`）。ORM 对象和 dict（用 `dict.get("raw_report")` 回退）都支持。MVP 优先支持 ORM 对象，dict 兼容通过 `getattr` + `dict.get` fallback。
