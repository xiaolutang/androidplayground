## 任务边界

### 做什么（IN scope）

1. **新建 `agent/diagnosis/playbook_executor.py`**（当前为空文件，待实现）：PlaybookExecutor 类，双模式编排器——根据 Playbook 的 `reproduce_steps` 是否非空，分发到复现模式或探测/诱发模式。

2. **复现模式（Mode A）**：Playbook 有 `reproduce_steps`（非空 list）→ 调 `reproduce_runner.run_reproduce()` 确定性顺序执行，BF003 不参与。输出 `list[ReproStep]`。

3. **探测/诱发模式（Mode B）**：Playbook 无明确脚本（`reproduce_steps` 为空）→ 起一个简单 while 循环 agent loop（MVP 不引 LangGraph 框架，见「关键决策 Q1」），每步：采集截图 → BF003 `vision_engine.decide()` 决策 → BF002 `adb_tools` 执行 action → BF004 `signal_router.dispatch()` 检查信号 → 命中信号或步数耗尽时终止。

4. **步数预算 D7 硬约束**：探测模式 agent loop 的 `max_steps` 为硬上限（默认 10，config 可覆盖），步数耗尽时立即终止 loop，不超预算。

5. **步数耗尽 → 创建 CapabilityGap**：探测模式步数耗尽（无信号命中）→ 调 `GapStore.create({gap_type: 'coverage', ...})` 创建覆盖率缺口，记录"步数耗尽未能诱发目标信号"。

6. **信号命中终止**：探测模式每步执行后检查 `SignalRouter.dispatch()` 返回值，命中 BB003 消费信号（crash/error/flutter_error/process 类）→ 立即 break loop。

7. **ExecutorResult 输出**：统一双模式产出为 `ExecutorResult` dataclass，含 `mode`（"reproduce" / "explore"）/ `repro_steps` / `signals` / `exhausted`（步数是否耗尽）/ `gap_created`（是否创建了缺口）/ `step_count` / `reasoning`（执行摘要）。

8. **截图采集**：探测模式每步采集 screenshot（BF002 `screenshot_collector.collect()` 或直接 `adb_tools.screenshot()`），转 data_url 喂 BF003 `vision_engine.decide(screenshot_url=...)`。

9. **action 分发执行**：探测模式 BF003 返回 `VisionDecision(action=..., params=...)`，Executor 将 action 映射到 BF002 `adb_tools` 函数执行（tap/swipe/input/press/back/screenshot/wait 共 7 类，与 BF003 action 白名单 + BF002 dispatch 表对齐）。

10. **单元测试**：`tests/unit/diagnosis/test_playbook_executor.py`，全 mock（reproduce_runner / vision_engine / adb_tools / signal_router / GapStore），覆盖复现模式 / 探测模式（预设 VisionDecision 序列）/ 步数耗尽→缺口 / 信号命中终止。

### 不做什么（OUT of scope）

- **不实现 LangGraph 状态机拓扑**：MVP 用简单 while 循环实现等效语义（见 Q1 决策）。LangGraph StateGraph 正式引入由 ORB01（Orchestrator）负责。
- **不实现 BB004 假设树消费**：Executor 产出 `ExecutorResult`（含 repro_steps + signals），BB004 HypothesisEngine 自行消费，不反向调用。
- **不持久化 Trajectory**：Executor 返回内存对象 `ExecutorResult`，持久化时机由 Orchestrator 决定（与 BF002 reproduce_runner 一致）。
- **不实现 Playbook 选择/路由**：BF006 PlaybookRegistry 负责按 symptom_type 检索 Playbook，Executor 接收已选定的 PlaybookDefinition。
- **不实现 BF003 视觉决策内部逻辑**：Executor 调 `vision_engine.decide()`，BF003 内部 LLM 调用 / 锚点对照 / fallback 由 BF003 自行处理。Executor 不关心 LLM 细节。
- **不实现 BF004 信号监听长连接**：Executor 调 `signal_router.dispatch()` 检查已有信号。BF004 信号采集（logcat/flutter/process/visual 四类监听）由 BF004 负责，Executor 消费其产出。
- **不实现 emulator 管理**：Executor 接收已就绪的 `ADBClient`（device 已 boot 完成），emulator 启停由 BF002 EmulatorPool / Orchestrator 负责。
- **不做 async 接口**：Executor `execute()` 为同步 `def`（MVP 串行执行，与 BF002 风格一致）。BF003 `vision_engine.decide()` 为 async，Executor 内部用 `asyncio.run()` 同步调用。
- **不实现 tool 描述/JSON Schema**：Executor 直接调用 `adb_tools` 函数（Python 函数调用），不生成 agent tool 描述供 LLM tool-calling。BF003 `vision_engine.decide()` 返回结构化 `VisionDecision`，Executor 解释其 action 字段分发。

## 验收标准（可测试）

### AC-1：双模式分发

- **断言**：`PlaybookExecutor(...).execute(playbook)` 当 `playbook.reproduce_steps` 非空（list 长度 > 0）→ 走复现模式，`result.mode == "reproduce"`。
- **断言**：`playbook.reproduce_steps` 为空 list → 走探测模式，`result.mode == "explore"`。
- **断言**：模式判定仅基于 `reproduce_steps` 是否非空，不参考 `passive` / `hypothesis_space` / `signal_triggers` 等其他字段。

### AC-2：复现模式（确定性脚本）

- **断言**：复现模式调用 `reproduce_runner.run_reproduce(client, playbook.reproduce_steps, ...)`，传入 Playbook 的 reproduce_steps 脚本。
- **断言**：复现模式不调用 `vision_engine.decide()`（BF003 不参与）。
- **断言**：`run_reproduce` 返回的 `list[StepOutcome]` 经 `outcomes_to_repro_steps()` 转换为 `list[ReproStep]`，写入 `ExecutorResult.repro_steps`。
- **断言**：复现模式 `exhausted=False`（步数预算不约束确定性脚本）、`gap_created=False`（复现模式不创建缺口）。
- **断言**：复现模式 `signals` 为空 list（信号采集由 reproduce_runner 内部 logcat fallback 处理，写入 ReproStep.actual_signal；Executor 层不二次采集）。

### AC-3：探测模式 agent loop（while 循环）

- **断言**：探测模式执行循环 `while step < max_steps:`，每步依次：采集截图 → `vision_engine.decide()` → 执行 action → 检查信号。
- **断言**：循环体内 step 计数从 1 递增，每步完成后 `step += 1`。
- **断言**：`vision_engine.decide(screenshot_url=..., task_description=...)` 被调用（传入当前步采集的截图 data_url + Playbook 任务描述）。
- **断言**：`VisionDecision.action` 映射到 `adb_tools` 函数执行（tap→adb_tools.tap / swipe→adb_tools.swipe / ...）。
- **断言**：`VisionDecision.action == "wait"` 时调 `time.sleep(params["duration_ms"]/1000)`，不调 adb_tools。
- **断言**：`VisionDecision.action == "screenshot"` 时仅采集截图（已在该步开头采集），不重复调 adb_tools。
- **断言**：每步产出一个 `ReproStep`（含 action / target_coords 或 target_text / screenshot_ref），追加到 `repro_steps`。

### AC-4：步数预算 D7 硬约束

- **断言**：`max_steps` 默认值为 10（D7 design 默认：单假设验证 5 步，探测模式给 10 步余量）。
- **断言**：`max_steps` 可通过构造函数参数覆盖（`PlaybookExecutor(..., max_steps=5)`）。
- **断言**：循环条件 `step < max_steps` 为硬约束——达到 max_steps 时立即退出循环，不会多执行一步。
- **断言**：步数耗尽时 `result.exhausted=True`，`result.step_count == max_steps`。

### AC-5：步数耗尽 → 创建 CapabilityGap

- **断言**：探测模式步数耗尽（`step == max_steps` 且无信号命中）→ 调 `GapStore.create({id: <uuid>, gap_type: 'coverage', description: 'step budget exhausted: ...', linked_bug_ids: [], ...})`。
- **断言**：创建的 CapabilityGap `status == 'identified'`（GapStore.create 强制覆盖）。
- **断言**：`result.gap_created=True`（标记已创建缺口）。
- **断言**：GapStore.create 失败（DB 异常）时，仅 `logging.warning`，不掩盖执行结果——ExecutorResult 仍正常返回（gap_created=False，exhausted=True），由 Orchestrator 决定后续降级。
- **断言**：`gap_type` 为 `"coverage"`（步数耗尽属覆盖率缺口，非设施缺口 facility）。

### AC-6：信号命中终止 loop

- **断言**：探测模式每步执行后调 `signal_router.dispatch(signal)` 检查信号。
- **断言**：`dispatch` 返回非空结果（至少一个消费方处理了信号）→ 立即 break loop，`result.exhausted=False`。
- **断言**：命中的信号追加到 `result.signals`（list[dict]）。
- **断言**：信号命中时 `result.gap_created=False`（有信号命中说明探测成功，不创建缺口）。
- **断言**：`signal_router.dispatch` 返回空 list（无消费方注册 / 无信号）→ 继续下一步。

### AC-7：action 工具执行（7 类）

- **断言**：`VisionDecision.action == "tap"` → 调 `adb_tools.tap(client, x=params["x"], y=params["y"], device_id=...)`。
- **断言**：`action == "swipe"` → 调 `adb_tools.swipe(client, x1, y1, x2, y2, duration_ms=params.get("duration_ms", 300), device_id=...)`。
- **断言**：`action == "input"` → 调 `adb_tools.input_text(client, text=params["text"], device_id=...)`。
- **断言**：`action == "press"` → 调 `adb_tools.press_key(client, keycode=params["keycode"], device_id=...)`。
- **断言**：`action == "back"` → 调 `adb_tools.press_key(client, keycode="4", device_id=...)`（back 固定 keycode="4"）。
- **断言**：`action == "screenshot"` → 不调 adb_tools 动作函数（截图已在该步开头采集）。
- **断言**：`action == "wait"` → 调 `time.sleep(params["duration_ms"] / 1000.0)`，不调 adb_tools。
- **断言**：BF002 ADBError 家族异常（ADBConnectionError / ADBCommandError / ADBTimeoutError）在探测模式下单步失败时捕获记录到 ReproStep，不中断 loop（继续下一步，与复现模式 abort 默认不同——探测模式容错探索）。

### AC-8：ExecutorResult 输出结构

- **断言**：`ExecutorResult` 为 dataclass，字段：`mode: str`（"reproduce" / "explore"）/ `repro_steps: list[ReproStep]` / `signals: list[dict]` / `exhausted: bool` / `gap_created: bool` / `step_count: int` / `reasoning: str`。

- **断言**：探测模式 `mode="explore"` / `step_count` 为实际执行步数（<= max_steps）。
- **断言**：`reasoning` 为非空字符串，含执行摘要（如 "reproduce mode: 3 steps executed" 或 "explore mode: signal hit at step 5, action=tap"）。

### AC-9：截图采集（探测模式每步）

- **断言**：探测模式每步开头采集截图（调 `screenshot_collector.collect(client, device_id=...)` 或 `adb_tools.screenshot(client, device_id=...)` 返回 data_url）。

## 关键决策

### Q1：LangGraph vs 简单 while 循环？

**决策：方案 A（简单 while 循环）**。

理由：
1. MVP 阶段 LangGraph 框架引入增加依赖且 StateGraph 拓扑对单 loop 场景过重。
2. 探测模式语义简单：`while step < max_steps: 截图→决策→执行→检查信号`，while 循环可完整表达。
3. 可测试性：while 循环 mock vision_engine 预设序列即可测试，无需 LangGraph test client。
4. ORB01（Orchestrator）正式引入 LangGraph 时，可将本 Executor 的 loop 体重构为 StateGraph node，接口不变（`execute(playbook) -> ExecutorResult`）。
5. Contract 明确记录此决策，ORB01 时作为重构依据。

**不引 LangGraph 依赖**：`requirements.txt` / `pyproject.toml` 不新增 `langgraph`。Executor 仅用标准库 + BF002/BF003/BF004 既有接口。

### Q2：探测模式 BF003 decide() 是 async，Executor 是 sync，如何调用？

**决策：Executor 内部用 `asyncio.run()` 同步调用**。

```python
import asyncio

decision = asyncio.run(
    self._vision_engine.decide(
        screenshot_url=screenshot_url,
        task_description=task_description,
    )
)
```

理由：
1. Executor 保持同步接口（与 BF002 reproduce_runner 风格一致，Orchestrator 调用简单）。
2. BF003 decide() 为 async 因 LLM 调用原生 async（INF04 LLMGateway），Executor 适配。
3. `asyncio.run()` 每步创建新事件循环，MVP 串行无并发问题。
4. 若未来 Executor 转 async（ORB01 LangGraph async），去掉 `asyncio.run()` 即可。

### Q3：步数耗尽创建的缺口 gap_type 为什么是 coverage 而非 facility？

**决策：gap_type = "coverage"**。

理由：
1. `facility` 缺口指"基础设施不可用"（如 emulator 启动失败、ADB 不通）——BF002 已用。
2. 步数耗尽属于"探测能力覆盖不足"——agent 在给定步数预算内未能诱发目标信号，是探索覆盖率问题。
3. `coverage` 缺口语义：需要更多探测策略 / 更大步数预算 / 更丰富的 Playbook 才能覆盖此 bug 的复现路径。
4. 与 design 5.4 缺口回流一致：coverage 缺口 → BB010 诊断 → BB015 补齐（录入新 Playbook / 调整步数预算）→ BB011 检测补齐 → reflow。

### Q4：探测模式单步 ADB 失败是否中断 loop？

**决策：不中断，记录错误继续下一步**。

理由：
1. 探测模式本质是探索性的——某步 tap 坐标可能因 UI 变化而 miss，不应因此放弃整个探索。
2. BF003 fallback 决策（action="wait"）也可能执行，Executor 应容错。
3. 与复现模式不同：复现模式确定性脚本有 expected 行为，单步失败可能意味脚本失效（abort）；探测模式无 expected，单步失败是正常探索代价。
4. 错误记录到该步 ReproStep（actual_signal 记录 error），不创建缺口（缺口仅在步数耗尽时创建）。

### Q5：Executor 如何获取 task_description 传给 BF003？

**决策**：从 PlaybookDefinition 构造描述。

```python
task_description = (
    f"Bug 症状类型: {playbook.symptom_type}, "
    f"信号触发关键字: {', '.join(playbook.signal_triggers)}, "
    f"目标: 探索 UI 诱发目标信号或定位异常"
)
```

理由：
1. PlaybookDefinition 含 `symptom_type` / `signal_triggers`，可拼成 task 描述供 BF003 LLM 理解当前目标。
2. 不从 BugReport 取详细描述（Executor 不直接接 BugReport，解耦）——Orchestrator 可在调用 Executor 前将 BugReport 关键信息注入 Playbook.metadata，Executor 优先读 metadata.get("task_description")。

## 实现要点

### 类设计

```python
@dataclass
class ExecutorResult:
    mode: str  # "reproduce" / "explore"
    repro_steps: list[ReproStep]
    signals: list[dict]
    exhausted: bool
    gap_created: bool
    step_count: int
    reasoning: str


class PlaybookExecutor:
    def __init__(
        self,
        *,
        client: ADBClient,
        vision_engine: VisionDecisionEngine | None = None,  # 探测模式必传
        signal_router: SignalRouter | None = None,          # 探测模式必传
        gap_store: GapStore | None = None,                   # 步数耗尽建缺口
        device_id: str | None = None,
        max_steps: int = 10,                                 # D7 默认
        screenshot_collector_fn = None,                      # 可注入（测试 mock）
    ) -> None: ...

    def execute(self, playbook: PlaybookDefinition) -> ExecutorResult:
        if playbook.reproduce_steps:
            return self._execute_reproduce(playbook)
        else:
            return self._execute_explore(playbook)
```

### 复现模式实现

```python
def _execute_reproduce(self, playbook: PlaybookDefinition) -> ExecutorResult:
    outcomes = run_reproduce(
        self._client,
        playbook.reproduce_steps,
        device_id=self._device_id,
    )
    repro_steps = outcomes_to_repro_steps(outcomes)
    return ExecutorResult(
        mode="reproduce",
        repro_steps=repro_steps,
        signals=[],  # 信号在 ReproStep.actual_signal 内
        exhausted=False,
        gap_created=False,
        step_count=len(repro_steps),
        reasoning=f"reproduce mode: {len(repro_steps)} steps executed",
    )
```

### 探测模式实现

```python
def _execute_explore(self, playbook: PlaybookDefinition) -> ExecutorResult:
    task_description = self._build_task_description(playbook)
    repro_steps: list[ReproStep] = []
    signals: list[dict] = []
    step = 0
    exhausted = False

    while step < self._max_steps:
        step += 1
        # 1. 采集截图
        screenshot_url = self._capture_screenshot()  # 可能 None

        # 2. BF003 决策
        decision = asyncio.run(
            self._vision_engine.decide(
                screenshot_url=screenshot_url or "",
                task_description=task_description,
            )
        )

        # 3. 执行 action
        repro_step = self._execute_action(decision, step)
        repro_steps.append(repro_step)

        # 4. 检查信号
        step_signals = self._check_signals()
        if step_signals:
            signals.extend(step_signals)
            break

        # 5. 步数耗尽检查
        if step >= self._max_steps:
            exhausted = True

    # 步数耗尽 → 创建缺口
    gap_created = False
    if exhausted and not signals:
        gap_created = self._create_coverage_gap(playbook, step)

    return ExecutorResult(
        mode="explore",
        repro_steps=repro_steps,
        signals=signals,
        exhausted=exhausted,
        gap_created=gap_created,
        step_count=step,
        reasoning=self._build_reasoning(step, signals, exhausted),
    )
```

### action 分发表（探测模式）

| VisionDecision.action | adb_tools 函数 | params 消费 |
|----------------------|---------------|------------|
| `tap` | `adb_tools.tap(client, x, y, device_id=...)` | `params["x"], params["y"]` |
| `swipe` | `adb_tools.swipe(client, x1, y1, x2, y2, duration_ms, device_id=...)` | `params["x1"],["y1"],["x2"],["y2"],["duration_ms"]` |
| `input` | `adb_tools.input_text(client, text, device_id=...)` | `params["text"]` |
| `press` | `adb_tools.press_key(client, keycode, device_id=...)` | `params["keycode"]` |
| `back` | `adb_tools.press_key(client, keycode="4", device_id=...)` | 固定 "4" |
| `screenshot` | （no-op，截图已采集） | 无 |
| `wait` | `time.sleep(params["duration_ms"] / 1000.0)` | `params["duration_ms"]` |

## 风险与降级

| 风险 | 影响 | 降级 |
|------|------|------|
| BF003 LLM 延迟高（每步 2-5s） | 探测模式 max_steps=10 可能耗时 20-50s | max_steps 可配（config `EXPLORE_MAX_STEPS=10`），Orchestrator 可按超时降级 |

| 信号采集时序：action 执行后信号尚未到达 logcat | signal_router.dispatch 可能漏信号 | MVP 接受最终一致性（步末检查）；BF004 长连接流式监听实现后可改为步间持续监听 |
| asyncio.run() 嵌套（Executor 在 async 上下文被调） | RuntimeError: asyncio.run() cannot be called from a running event loop | MVP Executor 为同步调用（Orchestrator 同步调），无嵌套；若 ORB01 转 async，去掉 asyncio.run() |
| 探测模式 ReproStep.id 为空 | 持久化时需填充 | 与 BF002 一致：id 留空字符串占位，Orchestrator 持久化时填充 |
