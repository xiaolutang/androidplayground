## 任务边界

### 做什么（IN scope）

1. **新建 `agent/diagnosis/hypothesis_engine.py`**：HypothesisEngine 类——封装假设树状态机（4 态迁移）、换方向（回溯父切兄弟）、根因回退（rootcause.overturned）、步数预算 D7、负向知识反查剪枝。内部闭环，不外泄 Orchestrator（analysis 第 489 行）。

2. **4 态迁移矩阵**（`_STATE_TRANSITIONS`）：proposed → verifying → {confirmed | refuted}；非法迁移抛 `HypothesisTransitionError`。状态枚举复用 SCH01 已定义的 `HypothesisStatus`（PROPOSED/VERIFYING/CONFIRMED/REFUTED）。

3. **换方向（`refute_and_pivot`）**：当前假设 refuted → 回溯 parent_id → 切下一个 `proposed` 兄弟；无兄弟 → 继续上溯；到根仍无兄弟 → 返回 None（诊断失败，由 Orchestrator 转缺口/结束）。

4. **根因回退（`overturn_root_cause`）**：confirmed 根因被 fixing/regression 阶段新信号推翻 → status 从 confirmed 迁移到 refuted + `is_rootcause` 置回 False + 记录 `overturning_signal` / `overturning_stage`（与 SCH01 Hypothesis schema 字段对齐，analysis 第 793-794 行）。overturn 后触发换方向（pivot）。

5. **步数预算 D7 硬约束（`check_budget_and_pivot`）**：`max_steps`（默认 20，config 可覆盖——单 bug 全局排查步数 design 默认 30，本引擎管假设验证子预算）为硬上限。步数耗尽时：(a) refute 当前假设；(b) **不**换方向（与 design 第 799 行一致：全局预算耗尽→不再换方向）；(c) 调 `GapStore.create({gap_type: 'coverage', ...})` 转缺口诊断。返回 True 表示预算耗尽。

6. **步数耗尽转缺口**：调 `gap_store.create({id: <uuid>, gap_type: 'coverage' | 'reasoning', ...})`，gap_type 取决于耗尽上下文——纯步数耗尽属 `coverage`（探索覆盖率不足），根因被推翻后预算耗尽属 `reasoning`（推理路径穷尽）。

7. **refuted 永久保留（INV-2）**：`delete()` 方法始终抛 `HypothesisDeleteError`（与 GapStore.delete 模式一致，INV-2 第 47 行 + AP-1 第 75 行）。refuted 节点只能改 status/overturning 字段，不可物理删除。

8. **负向知识反查剪枝（`negate_and_prune`）**：调 `KBRetriever.negate_hypotheses(hypothesis_vectors=..., symptom_type=...)`，对返回的 `NegativeVerdict` 列表处理：`prune=True` → 直接 refute 该假设；`demote_factor < 1.0` → 降权标记（写入 hypothesis metadata，供 BB005 根因定位参考）。返回被 prune 的 hypothesis_id 列表。

9. **假设树构建（`propose`）**：`propose(parent_id, content, expected_signal=None) -> HypothesisNode`——创建新 `proposed` 节点，挂到 parent 的 children 列表（parent_id=None 为根假设）。

10. **内存表示（`HypothesisNode` dataclass）**：字段 id / parent_id / content / status / expected_signal / verifying_action / step_budget / step_used / confirming_evidence / falsifying_signal / overturning_signal / overturning_stage / is_rootcause / children: list[HypothesisNode]。与 SCH01 Hypothesis schema 字段一一对应，本引擎内存操作，持久化由调用方（Orchestrator）负责。

11. **单元测试**：`tests/unit/diagnosis/test_hypothesis_engine.py`，全 mock（GapStore / KBRetriever），覆盖 4 态迁移矩阵 / 换方向回溯 / 根因回退 overturn / 步数耗尽转缺口 / INV-2 delete 禁止 / 负向反查剪枝 prune + demote。

### 不做什么（OUT of scope）

- **不持久化 Hypothesis**：本引擎为内存状态机（dict[id, HypothesisNode]），不写 DB。持久化（SCH01 Hypothesis ORM 落库）由调用方（Orchestrator / BB005 根因定位器）在适当时机 flush。本引擎调 `gap_store.create` 仅为步数耗尽转缺口这一副作用。
- **不实现 LangGraph 集成**：MVP 用纯 Python 内存状态机实现等效语义（与 BB003 Q1 决策一致：MVP 不引 LangGraph 框架）。LangGraph StateGraph 正式引入由 ORB01（Orchestrator）负责，届时可将本引擎的方法映射为 StateGraph nodes/edges。
- **不实现 BB005 根因定位逻辑**：本引擎只管假设树状态机 + 回溯 + 步数预算 + 负向反查。BB005（root_cause_locator）负责从 confirmed 假设提炼根因，是独立任务。
- **不实现 BB003 Playbook 执行**：本引擎不调 PlaybookExecutor。假设验证的执行（复现/探测）由 Orchestrator 编排：Orchestrator 调 BB003 执行 → 喂信号给 BB004 判迁移。
- **不做向量化**：`negate_and_prune` 接收已向量化的 `hypothesis_vectors: list[list[float]]`，向量化由调用方负责（与 KBRetriever.negate_hypotheses 接口对齐）。
- **不实现 Trajectory 聚合**：Trajectory（root_hypothesis_id / total_step_used / total_step_budget）由 Orchestrator 管理，本引擎仅操作假设树内部状态。
- **不做 async 接口**：所有方法为同步 `def`（纯内存操作 + 同步调 gap_store / kb_retriever）。

## 验收标准（可测试）

### AC-1：4 态迁移矩阵

- **断言**：合法迁移 `proposed → verifying`（`verify()`）、`verifying → confirmed`（`confirm()`）、`verifying → refuted`（`refute()`）均成功，节点 status 更新。
- **断言**：`proposed → confirmed`（跳过 verifying）抛 `HypothesisTransitionError`。
- **断言**：`confirmed → verifying`（已 confirmed 回退）抛 `HypothesisTransitionError`。
- **断言**：`refuted → proposed`（refuted 复活）抛 `HypothesisTransitionError`。
- **断言**：`refute()` 可从任意非 refuted 状态迁移到 refuted（verifying → refuted 为常规；confirmed → refuted 仅经 `overturn_root_cause` 走特殊路径，不直接调 refute）。
- **断言**：`_STATE_TRANSITIONS` 定义为 `dict[HypothesisStatus, frozenset[HypothesisStatus]]`，与 GapStore `_STATE_TRANSITIONS` 模式一致。

### AC-2：换方向（refute_and_pivot）

- **断言**：当前节点 refuted 后，`refute_and_pivot` 回溯 parent_id → 返回 parent 下第一个 `proposed` 状态的兄弟节点。
- **断言**：parent 下无 `proposed` 兄弟（均已 verifying/confirmed/refuted）→ 继续上溯 grandparent，找其 children 中的 `proposed`。
- **断言**：上溯到根假设仍无 `proposed` 兄弟 → 返回 None（换方向失败，诊断路径穷尽）。
- **断言**：`refute_and_pivot` 先执行 refute（status → refuted），再执行 pivot（回溯找兄弟），两步原子语义。
- **断言**：refuted 兄弟不参与 pivot 候选（refuted 永久保留但不重选，INV-2）。

### AC-3：根因回退（overturn_root_cause）

- **断言**：`overturn_root_cause(root_id, reason, overturning_signal, overturning_stage)` 对 confirmed + is_rootcause=True 的节点：status confirmed → refuted + is_rootcause → False + 记录 overturning_signal / overturning_stage。
- **断言**：对非 confirmed 节点调 overturn 抛 `HypothesisTransitionError`（只有 confirmed 根因能被推翻）。
- **断言**：overturn 后自动触发 pivot（调 `refute_and_pivot` 逻辑），返回下一个 proposed 兄弟。
- **断言**：overturning_stage 取值为 `"fixing"` / `"verifying"` / `"regression"` 之一（与 SCH01 Hypothesis.overturning_stage 注释一致，analysis 第 793 行）。
- **断言**：overturned 节点 status=refuted 但保留 overturning_signal 记录（区分"验证失败 refuted"与"被推翻 refuted"，供负向知识沉淀）。

### AC-4：步数预算 D7 硬约束（check_budget_and_pivot）

- **断言**：`max_steps` 默认值为 20（D7 design 默认：全局排查 30 步，假设验证子预算取 20 留余量给修复/回归）。
- **断言**：`max_steps` 可通过构造函数参数覆盖（`HypothesisEngine(..., max_steps=10)`）。
- **断言**：`step_used >= max_steps` 时 `check_budget_and_pivot` 返回 True（预算耗尽）。
- **断言**：预算耗尽时：(a) 当前假设被 refute；(b) **不**执行换方向（不调 pivot 逻辑）；(c) 调 `gap_store.create` 转缺口。
- **断言**：预算未耗尽时 `check_budget_and_pivot` 返回 False，不 refute、不创建缺口。

### AC-5：步数耗尽转缺口

- **断言**：预算耗尽时调 `gap_store.create({id: <uuid>, gap_type: 'coverage', description: 'step budget exhausted: ...', linked_bug_ids: [], ...})`。
- **断言**：gap_type 默认 `"coverage"`（纯步数耗尽属探索覆盖率不足）。
- **断言**：若当前假设是 overturned 根因（根因被推翻后预算耗尽），gap_type 为 `"reasoning"`（推理路径穷尽）。
- **断言**：`gap_store` 为 None（未注入）时，步数耗尽仅 refute + 返回 True，不创建缺口（优雅降级，仅 logging.warning）。
- **断言**：`gap_store.create` 抛异常时捕获 + logging.warning，不掩盖引擎状态（refute 已生效，返回 True）。

### AC-6：refuted 永久保留（INV-2）

- **断言**：`delete(hypothesis_id)` 始终抛 `HypothesisDeleteError`（无论节点什么状态）。
- **断言**：refuted 节点的 status 可经 `overturn_root_cause` 迁移（confirmed→refuted），但 refuted 状态本身不可迁出（AC-1 已覆盖：refuted → 任何 抛错）。
- **断言**：`HypothesisDeleteError` 消息含 "INV-2" 提示（与 GapStore.GapDeleteError 模式一致）。
- **断言**：引擎内部 dict[id, HypothesisNode] 不提供任何物理删除入口（无 pop/del 操作 refuted 节点）。

### AC-7：负向知识反查剪枝（negate_and_prune）

- **断言**：`negate_and_prune(hypothesis_vectors, symptom_type)` 调 `kb_retriever.negate_hypotheses(hypothesis_vectors=..., symptom_type=...)` 获取 `list[NegativeVerdict]`。
- **断言**：`verdict.prune == True`（相似度 > 0.85）→ 对应假设直接 refute（status → refuted），返回的 pruned_ids 含该 hypothesis_id。
- **断言**：`verdict.demote_factor < 1.0`（0.6-0.85 区间）→ 该假设标记降权（写入 HypothesisNode.demote_factor 字段），**不**refute，不在 pruned_ids 中。
- **断言**：`verdict.prune == False and demote_factor == 1.0`（< 0.6 或无匹配）→ 该假设不受影响。
- **断言**：`kb_retriever` 为 None（未注入）时，`negate_and_prune` 直接返回空 list（无负向知识，不剪枝，优雅降级）。
- **断言**：`kb_retriever.negate_hypotheses` 抛异常时捕获 + logging.warning，返回空 list（负向反查失败不阻断主流程）。

### AC-8：假设树构建（propose）

- **断言**：`propose(parent_id=None, content="...")` 创建根假设（parent_id=None），status=proposed，返回 HypothesisNode。
- **断言**：`propose(parent_id="hyp_001", content="...")` 创建子假设，挂到 hyp_001 的 children 列表尾部。
- **断言**：`propose(parent_id="nonexistent")` 抛 `ValueError`（父节点不存在）。
- **断言**：新节点 id 为自动生成的 UUID（`uuid.uuid4().hex`），全局唯一。
- **断言**：`expected_signal` 参数可选传入，写入 HypothesisNode.expected_signal（供验证时比对）。

### AC-9：内存表示（HypothesisNode dataclass）

- **断言**：`HypothesisNode` 为 `@dataclass`，字段：`id: str` / `parent_id: str | None` / `content: str` / `status: HypothesisStatus` / `expected_signal: dict | None` / `verifying_action: dict | None` / `step_budget: int | None` / `step_used: int` / `confirming_evidence: dict | None` / `falsifying_signal: dict | None` / `overturning_signal: dict | None` / `overturning_stage: str | None` / `is_rootcause: bool` / `children: list[HypothesisNode]` / `demote_factor: float`（默认 1.0）。
- **断言**：字段与 SCH01 `Hypothesis` ORM schema 一一对应（id/parent_id/hypothesis_text→content/expected_signal/verify_action→verifying_action/step_budget/step_used/status/confirming_evidence/falsifying_signal/overturning_signal/overturning_stage/is_rootcause）。
- **断言**：`status` 默认值 `HypothesisStatus.PROPOSED`（与 SCH01 schema default 一致）。
- **断言**：`children` 默认空 list，`is_rootcause` 默认 False，`step_used` 默认 0。

- **断言**：单元测试全 mock，覆盖以下场景：
  - 4 态合法迁移：propose → verify → confirm / refute 各路径断言 status 正确。
  - 4 态非法迁移：proposed→confirmed / confirmed→verifying / refuted→proposed 断言抛 HypothesisTransitionError。
  - 换方向正常：构造 3 层树（root → child_a(refuted) → grandchild）+ child_b(proposed) → refute_and_pivot 返回 child_b。
  - 换方向穷尽：单链树（root → only_child）→ refute only_child → pivot 上溯到 root 无兄弟 → 返回 None。
  - 根因回退：confirmed + is_rootcause=True → overturn_root_cause → status=refuted + is_rootcause=False + overturning_signal/stage 记录 + pivot 返回兄弟。
  - 步数耗尽：max_steps=3 + step_used=3 → check_budget_and_pivot 返回 True + refute 当前 + GapStore.create 被调（gap_type=coverage）。

  - 负向反查 prune：mock negate_hypotheses 返回 prune=True verdict → negate_and_prune refute 该假设 + 返回 pruned_ids。

  - 负向反查降级：kb_retriever=None → 返回空 list 不阻断。
  - GapStore=None 降级：步数耗尽 + gap_store=None → refute 生效 + 返回 True + 无缺口创建。

## 关键决策

### Q1：内存状态机 vs LangGraph StateGraph？

**决策：方案 A（纯 Python 内存状态机）**。

理由：
1. MVP 阶段 LangGraph 框架引入由 ORB01 统一负责，BB004 作为业务组件应保持框架无关。
2. 假设树状态机语义（4 态迁移 + 回溯 + 步数预算）用纯 Python dict + 方法即可完整表达，无需 StateGraph 拓扑。
3. 可测试性：内存状态机 mock gap_store / kb_retriever 即可全路径测试，无需 LangGraph test client。
4. ORB01 引入 LangGraph 时，可将本引擎方法映射为 StateGraph nodes（propose→node, verify→node, refute_and_pivot→conditional_edge），接口不变。

**不引 LangGraph 依赖**：`requirements.txt` / `pyproject.toml` 不新增 `langgraph`。

### Q2：步数预算是全局还是单假设？

**决策：本引擎管单假设验证步数（step_used per hypothesis），全局预算由 Trajectory.total_step_used 管理。**

理由：
1. SCH01 Hypothesis schema 有 `step_budget` / `step_used`（单假设级），Trajectory 有 `total_step_budget` / `total_step_used`（全局级）——两层预算。
2. 本引擎的 `check_budget_and_pivot` 检查的是当前假设的 `step_used >= step_budget`（单假设耗尽）+ 引擎级 `max_steps`（全局硬上限，防失控）。
3. 全局预算（Trajectory 层）的检查由 Orchestrator 负责（调本引擎前先查 Trajectory.total_step_used），本引擎不直接读 Trajectory。
4. `max_steps` 构造函数参数作为引擎级安全阀（默认 20），与单假设 step_budget（默认 5，design D7）是两个独立约束。

### Q3：步数耗尽时为什么不换方向？

**决策：步数耗尽 → refute 当前 + 不换方向 + 转缺口（analysis 第 799 行明确）。**

理由：
1. design 第 799 行："全局步数预算耗尽 → 不再换方向，转 Tier3/4 缺口诊断。"
2. 语义：步数预算代表"本次排查的探索余量"，耗尽意味着已穷尽当前能力，继续换方向只会空转。
3. 与 refuted（验证失败）不同：refuted 后换方向是"这条路径走不通，试另一条"；步数耗尽是"整体探索能力不足"，需补齐能力（缺口）后 reflow。
4. 转缺口（coverage/reasoning）让 BB010 诊断根因，BB015 补齐后回流重试。

### Q4：negate_and_prune 的 hypothesis_vectors 从哪来？

**决策：由调用方（Orchestrator / BB005）负责向量化，本引擎只接收 list[list[float]]。**

理由：
1. 向量化依赖 embedding 模型（INF04 LLMGateway），本引擎作为纯业务状态机不应耦合 embedding 调用。
2. KBRetriever.negate_hypotheses 的接口已是 `hypothesis_vectors: list[list[float]]`（BF005 定义），本引擎透传。
3. 调用时机：Orchestrator 在 propose 批量假设后、verify 前，调本引擎 `negate_and_prune` 做预剪枝——此时向量由 Orchestrator 从 BB002/BB005 获取。

### Q5：HypothesisNode 与 SCH01 Hypothesis ORM 的关系？

**决策：HypothesisNode 是内存 dataclass，Hypothesis 是 ORM schema，字段一一对应但独立。**

理由：
1. 本引擎内存操作（dict[id, HypothesisNode]），不碰 ORM session。
2. 持久化时机由 Orchestrator 决定：从 HypothesisNode 字段映射到 Hypothesis ORM 行，批量 flush。
3. 字段命名对齐（content↔hypothesis_text / verifying_action↔verify_action），映射逻辑简单，放 Orchestrator 或 BB005。
4. 本引擎不提供 `to_orm()` / `from_orm()` 方法（避免耦合 SQLAlchemy），映射由调用方实现。

## 实现要点

### 类设计

```python
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any, Optional
import uuid

from agent.schemas.trajectory import HypothesisStatus
from agent.kb.retriever import KBRetriever, NegativeVerdict
from agent.gap.gap_store import GapStore


# 4 态迁移矩阵
_STATE_TRANSITIONS: dict[HypothesisStatus, frozenset[HypothesisStatus]] = {
    HypothesisStatus.PROPOSED: frozenset({HypothesisStatus.VERIFYING, HypothesisStatus.REFUTED}),
    HypothesisStatus.VERIFYING: frozenset({HypothesisStatus.CONFIRMED, HypothesisStatus.REFUTED}),
    HypothesisStatus.CONFIRMED: frozenset({HypothesisStatus.REFUTED}),  # 仅经 overturn 走此路径
    HypothesisStatus.REFUTED: frozenset(),  # 终态：不可迁出（INV-2）
}


class HypothesisTransitionError(Exception):
    """非法状态迁移。"""


class HypothesisDeleteError(Exception):
    """禁止删除 refuted 节点（INV-2）。"""


@dataclass
class HypothesisNode:
    """假设树节点（内存表示，与 SCH01 Hypothesis ORM 字段对齐）。"""
    id: str
    parent_id: Optional[str]
    content: str
    status: HypothesisStatus = HypothesisStatus.PROPOSED
    expected_signal: Optional[dict] = None
    verifying_action: Optional[dict] = None
    step_budget: Optional[int] = None
    step_used: int = 0
    confirming_evidence: Optional[dict] = None
    falsifying_signal: Optional[dict] = None
    overturning_signal: Optional[dict] = None
    overturning_stage: Optional[str] = None
    is_rootcause: bool = False
    children: list["HypothesisNode"] = field(default_factory=list)
    demote_factor: float = 1.0


class HypothesisEngine:
    """假设树引擎：4 态状态机 + 换方向 + 根因回退 + 步数预算 + 负向反查。

    封装回溯/根因回退/步数预算（内部闭环，不外泄 Orchestrator）。
    """

    def __init__(
        self,
        *,
```

### 迁移矩阵语义

| from | 合法 to | 场景 |
|------|---------|------|
| PROPOSED | VERIFYING | `verify()` 开始验证 |
| PROPOSED | REFUTED | `refute()` 直接否定（如负向反查 prune） |
| VERIFYING | CONFIRMED | `confirm()` 信号匹配 |
| VERIFYING | REFUTED | `refute()` 信号不符/步数耗尽 |
| CONFIRMED | REFUTED | 仅 `overturn_root_cause()` 走此路径 |
| REFUTED | （无） | 终态，INV-2 不可迁出 |

### 换方向算法

```python
def _find_next_proposed_sibling(self, node: HypothesisNode) -> Optional[HypothesisNode]:
    """从 node 开始向上回溯，找下一个 proposed 兄弟。"""
    current = node
    while current.parent_id is not None:
        parent = self._nodes[current.parent_id]
        # 在 parent.children 中找 current 之后的 proposed 兄弟
        for sibling in parent.children:
            if sibling.id != current.id and sibling.status == HypothesisStatus.PROPOSED:
                return sibling
        # 无兄弟 → 上溯
        current = parent
    return None  # 到根仍无
```

## 风险与降级

| 风险 | 影响 | 降级 |
|------|------|------|
| step_budget 与 max_steps 语义混淆 | 调用方可能只设一层预算 | Contract 明确：step_budget 为单假设级（默认 5），max_steps 为引擎级安全阀（默认 20），两者独立检查 |
| 换方向回溯深度过大（深层树） | pivot 性能退化为 O(depth × siblings) | MVP 假设树深度浅（design 假设 2-3 层），O(n) 可接受；深层树优化（如缓存 proposed 索引）留 ORB01 |
| 负向反查向量未就绪（embedding 服务不可用） | negate_and_prune 无法执行 | kb_retriever=None 时直接返回空 list（优雅降级，不剪枝）；调用方负责确保向量可用 |
| GapStore 未注入（Orchestrator 忘传） | 步数耗尽无法转缺口 | gap_store=None 时仅 refute + 返回 True + warning，Orchestrator 可后续补建缺口 |
| 内存 dict 无上限（长时间运行 OOM） | 大量假设堆积 | MVP 单次排查假设数有限（design 估算 < 50）；引擎为短生命周期对象（Orchestrator 每次 bug 新建），不跨 bug 复用 |
