## 任务边界

### 做什么（IN scope）

1. **新建 `agent/fix/auto_fixer.py`**（当前为空文件，待实现）：AutoFixer 类——封装三策略优先级修复（template → llm → history_calibration），接收根因定位结果 + Tier 分级 + KB 检索上下文，产出 `FixPatch`（含 strategy_chain 审计链）。纯业务逻辑，不持久化（持久化由调用方 Orchestrator 负责）。

2. **三策略优先级（`generate_patch`）**（design 5.1 第 760-761 行，strategy 字段取值 template/llm/history_calibration，FixPatch schema 第 594 行）：
   - 策略 1 **template**（KB pattern 套用）：从 `kb_context` 的 `pattern` 层检索结果中取 top1 pattern 套用——若 top1 similarity >= `TEMPLATE_SIMILARITY_THRESHOLD=0.7` 且 pattern 含 `patch_template` 字段，则模板渲染生成 patch。
   - 策略 2 **llm**（LLM 直生成）：调 `LLMGateway.complete(prompt_type="fix_patch", messages=...)`，model 经路由到 glm-5.1（D2），prompt 含 `root_cause_location` + `symptom_type` + unified diff 格式约束。LLM 失败重试上限 `FIX_RETRY_MAX`（config 默认 3），耗尽降级。
   - 策略 3 **history_calibration**（KB patch_history 校准）：从 `kb_context` 的 `patch_history` 层检索结果中取 top1 历史 patch 套用——若 top1 similarity >= `HISTORY_SIMILARITY_THRESHOLD=0.6` 且历史 patch 可用，则套用并标注 `kb_history_ref`。
   - 降级规则：每策略尝试失败（返回空 patch / 抛异常 / similarity 不达标）→ 降级到下一策略；三策略全失败 → 返回 `FixPatch`（patch_diff=None, strategy_chain 记录全部失败）。

3. **strategy_chain 审计链**（list，记录每策略 attempt，供审计/换策略回溯）：
   - 每次 strategy 尝试（无论成功失败）追加一条 `StrategyAttempt` 到 `strategy_chain`。
   - `StrategyAttempt` 字段：`strategy_name: str`（template/llm/history_calibration）/ `succeeded: bool` / `error: str | None`（失败原因）/ `latency_ms: int`（该策略耗时）/ `tokens_used: int | None`（仅 llm 策略有值，从 LLMResponse.usage 读取）/ `pattern_id: str | None`（template/history_calibration 命中的 KBEntry id）/ `attempt_no: int`（序号，从 1 递增）。
   - strategy_chain 最终写入 `FixPatch.strategy_chain`（JSON 列）。

4. **Tier1/Tier2 分流**（由调用方 BB006 ConfidenceEvaluator 传入 tier，本任务不重算 Tier）：
   - `tier=1`（Tier1 高置信）→ 产出 `FixPatch`（`is_draft=False`），patch 经三策略生成后直接用于 BB008 回归三关。
   - `tier=2`（Tier2 中置信）→ 产出 `FixPatch`（`is_draft=True` + `rationale="低置信度，需人工 review"`），patch 走轻量验证（design 5.1 第 778 行）。
   - `tier ∈ {3, 4}` → 不调用本修复器（由 Orchestrator 转缺口诊断 BB010，本任务不处理）。
   - **注意**：Tier 分级由 BB006 ConfidenceEvaluator 决定（Contract Q2），本任务接收 `tier: int` 参数，不重算。

5. **FixPatch 数据结构**（与 SCH01.3 `FixPatch` ORM schema 字段对齐，本任务产出内存对象，持久化由 Orchestrator 负责）：
   - `patch_content: str | None`（unified diff 格式，git apply 兼容；LLM prompt 约束输出格式）。
   - `files_changed: list[str]`（从 patch_content 解析或 LLM 输出提取）。
   - `strategy: str`（最终成功策略名；全失败时为最后尝试的策略名）。
   - `strategy_chain: list[dict]`（每策略 attempt 记录，见上）。
   - `pattern_id: str | None`（template/history_calibration 命中的 KBEntry id；llm 策略为 None）。
   - `is_draft: bool`（Tier1=False / Tier2=True）。
   - `rationale: str | None`（Tier2 时为"低置信度，需人工 review"；Tier1 时为 None）。
   - `tier: int`（从入参透传，1 或 2）。
   - `kb_history_ref: str | None`（history_calibration 策略命中的 KBEntry id，同 pattern_id）。

6. **LLM prompt 构造**（fix_patch prompt_type）：
   - System message：角色（你是 Android 客户端 bug 修复专家）+ 输出格式约束（unified diff，git apply 兼容，含 `--- a/` / `+++ b/` / `@@` hunk 标记）。
   - User message：`root_cause_location`（文件:行号 + 根因描述）+ `symptom_type`（症状类型）+ BugReport 摘要（复现步骤/堆栈关键行/版本）+ 历史 patch 参考（若有 kb_context patch_history top1，作为 few-shot 示例附入）。
   - 输出解析：LLMResponse.content 解析为 unified diff 字符串（strip 前后空白/markdown 代码块标记）；解析失败（空 content / 非 diff 格式）→ 视为该次重试失败。

7. **LLM 失败重试 + 降级**（D7 FIX_RETRY_MAX）：
   - llm 策略内重试：`LLMGateway.complete` 内部已有重试逻辑（INF04 已实现，重试上限 FIX_RETRY_MAX），本任务**不额外重试**——LLMGateway 抛 `LLMError` 即视为 llm 策略失败。
   - llm 策略失败 → strategy_chain 记录 `succeeded=False, error=<异常消息>` → 降级到 history_calibration 策略。
   - **注意**：LLMGateway 的重试针对"解析失败"（empty content / OpenAIError 非 timeout/ratelimit），超时/超限/HTTP 状态错误不重试直接抛。本任务捕获 `LLMError` 后记录并降级。

8. **KB 降级（冷启动优雅降级，design 5.3 第 821 行）**：
   - `kb_context` 为 None 或 `degraded=True`（冷启动 / 低相似度）→ template 策略直接跳过（similarity 不达标视为失败），history_calibration 策略也跳过 → 仅走 llm 策略（design 5.3 第 821 行："BB007 走 LLM 直生成不走 KB 校准"）。
   - `kb_context` 非 None 且 `degraded=False`，但 pattern 层无命中（entries 中无 `layer="pattern"`）→ template 策略失败（无可用模板），降级到 llm。
   - `kb_context` 非 None 且 `degraded=False`，pattern 层有命中但 top1 similarity < `TEMPLATE_SIMILARITY_THRESHOLD=0.7` → template 策略失败（相似度不足），降级到 llm。
   - KBRetriever 未注入（`kb_retriever=None`，构造函数参数）→ kb_context 视为 None，同冷启动降级。

9. **单元测试**：`tests/unit/fix/test_auto_fixer.py`，全 mock（LLMGateway / KBRetriever），覆盖三策略优先级 / 降级链 / Tier1/Tier2 分流 / strategy_chain 审计 / LLM 失败重试耗尽 / KB 冷启动降级 / 全策略失败兜底。

### 不做什么（OUT of scope）

- **不实现 patch 应用（git apply）**：本修复器只生成 `FixPatch`（patch_content + 元数据），不执行 git apply。应用由 BB008 回归验证器在验证阶段负责（Contract Q5）。
- **不实现回归验证**（BB008 负责）：BB008 负责三关验证（复现序列回归 + 既有测试 + 静态检查），本任务只产出 patch。
- **不实现 PR 提交**（BB009 负责）：BB009 负责 Tier1 提普通 PR / Tier2 提 draft PR。
- **不实现 Tier 分级**（BB006 负责）：Tier 由 BB006 ConfidenceEvaluator 决定，本任务接收 `tier` 参数。
- **不持久化 FixPatch**：本修复器为纯业务逻辑，返回内存中的 FixPatch 对象。DB 写入（关联 `BugReport.fix_patch_id`）由 Orchestrator 负责。
- **不实现 KB 检索**（BF005 负责）：修复器消费 `RetrievalResult`（kb_context），不自行调 `KBRetriever.retrieve`。调用方（Orchestrator）先检索再传入。
- **不实现根因定位**（BB005 负责）：修复器接收 `root_cause_location`（文件:行号 + 描述），不自行定位根因。
- **不实现 embedding 向量化**：kb_context 由调用方已检索完成（含相似度），本修复器不调 embedding。
- **不做 async 接口**：AutoFixer 为同步实现（LLMGateway.complete 是 async，本修复器内部 `asyncio.run` 或由调用方在 async 上下文中调用——MVP 用同步包装，因 Orchestrator 尚未确定 async/sync 模式）。

## 关键决策

### Q1：strategy_chain 是 list 还是单值？

**决策：list（记录每策略 attempt，供审计）。**

理由：
1. design FixPatch schema 有 `attempt_no / strategy_chain` 字段（第 599 行），F4a 换策略需要尝试历史。
2. list 形式记录每次策略尝试（含失败），供：(a) 审计回溯（为什么某策略失败）；(b) MetricPoint 统计（策略成功率）；(c) BB013 反思沉淀（从失败中学习改进 prompt/模板）。
3. `FixPatch.strategy` 字段（单值）记录最终成功策略，strategy_chain（list）记录完整尝试链——两者互补。
4. 与 BB004 HypothesisEngine 的假设树审计思路一致（refuted 节点保留供回溯）。

### Q2：Tier 分级由谁决定？

**决策：由调用方（BB006 ConfidenceEvaluator）传入 tier，本任务不重算。**

理由：
1. BB006 已实现三维打分 + Tier 分级（tier 1-4 确定性阈值规则），本任务不应重复实现。
2. 职责分离：BB006 负责"评估置信度 + 分级"，BB007 负责"按 Tier 产出对应 FixPatch"。
3. Orchestrator 编排：BB006 评估 → Orchestrator 消费 Tier 决定分流（tier 1/2 → BB007，tier 3/4 → BB010）→ BB007 接收 tier 参数产出 FixPatch。
4. 本任务仅处理 tier=1（is_draft=False）和 tier=2（is_draft=True），tier 3/4 不进入本修复器（Orchestrator 转缺口诊断）。

### Q3：LLM 失败重试次数？

**决策：FIX_RETRY_MAX（config 默认 3），LLMGateway 内部已重试，本任务不额外重试。**

理由：
1. INF04 LLMGateway 已实现重试逻辑：解析失败（empty content / OpenAIError 非 timeout/ratelimit）重试 FIX_RETRY_MAX 次，耗尽抛 LLMError。
2. 超时/超限/HTTP 状态错误不重试（直接抛 LLMError，避免放大故障）——这是 INF04 的设计决策，本任务遵循。
3. 本任务捕获 LLMError 后记录 strategy_chain 并降级到 history_calibration，不额外重试（避免双重重试放大 token 消耗）。
4. FIX_RETRY_MAX 参数化在 config（D7），环境变量可覆盖，测试可 monkeypatch。

### Q4：patch_content 格式？

**决策：unified diff（git apply 兼容），LLM prompt 约束输出格式。**

理由：
1. unified diff 是标准 patch 格式，git apply / patch 命令直接兼容，BB008 回归验证器可直接应用。
2. LLM prompt system message 约束输出格式：```
   输出格式：unified diff（git apply 兼容），格式如下：
   --- a/path/to/file
   +++ b/path/to/file
   @@ -line,count +line,count @@
   -old line
   +new line
   ```
3. 解析时 strip markdown 代码块标记（```diff ... ```），提取纯 diff 内容。
4. `files_changed` 从 `+++ b/` 行提取文件路径（去 `b/` 前缀），供 BB008/BB009 引用。

### Q5：是否实现 patch 应用（git apply）？

**决策：不实现，应用由 BB008 回归验证器在验证阶段负责。**

理由：
1. 职责分离：BB007 负责生成 patch（策略选择 + LLM/KB 调用 + 审计链），BB008 负责验证 patch（应用 + 三关回归）。
2. BB008 需要 git apply 后跑复现序列/既有测试/静态检查，应用 patch 是验证流程的一部分。
3. 本任务产出 `FixPatch` 对象（patch_content + 元数据），BB008 消费 patch_content 执行 git apply。
4. 若 patch 应用失败（git apply 冲突），由 BB008 反馈 → Orchestrator 决定是否重试（换策略/换 LLM 参数）。

### 三策略优先级流程

```
generate_patch(tier=1|2, kb_context=...)
│
├─ attempt 1: _try_template(kb_context, ...)
│   ├─ kb_context None / degraded → skip (succeeded=False, error="kb unavailable")
│   ├─ pattern 层无命中 → skip (succeeded=False, error="no pattern hit")
│   ├─ top1 similarity < 0.7 → skip (succeeded=False, error="similarity below threshold")
│   ├─ top1 无 patch_template → skip (succeeded=False, error="no patch_template")
│   └─ 成功 → patch_content = render(template), pattern_id = entry.id → 返回
│
├─ attempt 2: _try_llm(bug_report_summary, root_cause_location, ...)
│   ├─ llm_gateway None → skip (succeeded=False, error="llm_gateway unavailable")
│   ├─ LLMGateway.complete 抛 LLMError → catch (succeeded=False, error=异常消息)
│   ├─ content 为空/非 diff → skip (succeeded=False, error="empty or invalid diff")
│   └─ 成功 → patch_content = parse_diff(content), tokens_used = usage.total_tokens → 返回
│
├─ attempt 3: _try_history_calibration(kb_context, ...)
│   ├─ kb_context None / degraded → skip
│   ├─ patch_history 层无命中 → skip
│   ├─ top1 similarity < 0.6 → skip
│   └─ 成功 → patch_content = 历史 patch, pattern_id = entry.id → 返回
│
└─ 组装 FixPatch：
    ├─ patch_content = 首个成功策略的 patch（全失败则 None）
    ├─ strategy = 首个成功策略名（全失败则 "history_calibration"）
    ├─ strategy_chain = 全部 attempt 记录
    ├─ pattern_id / kb_history_ref = 命中策略的 entry.id
    ├─ is_draft = (tier == 2)
    ├─ rationale = TIER2_RATIONALE if tier == 2 else None
    └─ tier = 入参透传
```

### KB 层检索接口

```python
def _kb_pattern_top1(
    self, kb_context: Optional[RetrievalResult], threshold: float
) -> Optional[tuple[KBEntry, float]]:
    """取 kb_context 指定层 top1。

    kb_context.entries 按 similarity 降序排列（BF005 保证）。
    筛选 layer == "pattern"（template 策略）或 layer == "patch_history"
    （history_calibration 策略），取 top1 且 similarity >= threshold。
    """
    if kb_context is None or kb_context.degraded:
        return None
    for entry in kb_context.entries:
        # layer 字段在 KBEntry 上（BF005 schema）
        if entry.entry.layer == target_layer and entry.similarity >= threshold:
            return (entry.entry, entry.similarity)
    return None
```

## 风险与降级

| 风险 | 影响 | 降级 |
|------|------|------|
| LLM 生成的 patch 质量差（治标不治本/引入新 bug） | Tier1 PR 被拒 / 回归失败 | 三策略优先级（template/history 优先于 LLM）；BB008 回归三关拦截；BB013 反思沉淀改进 prompt |
| LLM 超时/超限（network 风险） | llm 策略失败 | LLMGateway 内部不重试超时/超限，直接抛 LLMError → 降级到 history_calibration |
| KB 冷启动（pattern 层为空） | template 策略无效 | kb_context=None/degraded 时跳过 template，走 llm 直生成（design 5.3 第 821 行） |
| 三策略全失败 | 无法自动修复 | FixPatch.patch_content=None，由 Orchestrator 转人工/缺口诊断 |
| strategy_chain 数据量大（长审计链） | JSON 列膨胀 | MVP 单次修复策略数固定 3（template/llm/history_calibration），chain 长度 ≤ 3，数据量可控 |
| LLM prompt 泄露敏感信息（代码内容） | 安全风险 | prompt 仅含 root_cause_location + symptom_type + 摘要，不含完整源码；MVP 内部使用，后续评估脱敏需求 |
