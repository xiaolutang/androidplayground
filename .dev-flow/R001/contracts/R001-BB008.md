## 任务边界

### 做什么（IN scope）

1. **新建 `agent/fix/regression_verifier.py`**：RegressionVerifier 类——封装三关验证编排（复现序列回归 + 既有测试 + 静态检查）、Tier 分级执行策略（Tier1 三关全过 / Tier2 轻量验证）、fail 分类（root_cause_error / patch_error）、信号返回（触发 BB004 根因回退或 BB007 重试）。

2. **Tier1 三关全过才提普通 PR**（backend 5.1 第 778 行 "Tier1 必须过 BB008 回归三关后才提普通 PR"）：
   - **第一关：复现序列回归**（BF002 `run_reproduce` 重放 + StepOutcome 比对）——用原始复现脚本在修复后的 worktree 上重跑，比对每步 `StepOutcome.action` + `expected_signal` 与 baseline 的一致性。修复成功意味着原 bug 的异常信号不再出现。
   - **第二关：既有测试**——执行项目的既有测试套件（`test_command` 可配置，如 `pytest tests/` 或 `flutter test`），全过才算通过。
   - **第三关：静态检查**——执行配置的静态检查命令（`static_check_commands`，默认 `["ruff check .", "mypy ."]`），全过才算通过。
   - 三关全过 → `VerificationResult(passed=True)`，调用方可提普通 PR。

3. **Tier2 轻量验证 + is_draft**（backend 5.1 第 778 行 "Tier2 走轻量验证：至少静态检查 + 可验证子集"）：
   - **静态检查**——同 Tier1 第三关（执行 `static_check_commands`）。
   - **可验证子集**——执行配置的测试子集命令（`tier2_test_subset_command`，如 `pytest tests/unit/`），非全量测试。
   - 轻量验证通过 → `VerificationResult(passed=True, tier=2)`，调用方提 draft PR（`is_draft=true`）。
   - 轻量验证不强制复现序列回归（Tier2 表示自动验证能力不足，强制三关会卡死）。

4. **三关执行顺序**（短路）：复现序列回归（最早）→ 既有测试 → 静态检查（最晚）。任一关 fail 即终止后续关卡，短路返回。

5. **fail 分类**（backend 5.1 第 764-766 行 "fail-根因错 → BB004 根因回退 / fail-补丁问题 → BB007 重试"）：
   - **root_cause_error**（根因错）：复现序列回归关 fail——修复后重跑复现序列，原 bug 的异常信号**仍然出现**。语义：根因方向错了，修了 A 也没用（甚至可能修错地方了）。返回信号触发 BB004 `overturn_root_cause`（根因回退，重下钻假设树）。
   - **patch_error**（补丁错）：复现序列回归关通过（原 bug 信号消失），但既有测试或静态检查关 fail。语义：根因方向对，但补丁引入了副作用 / 破坏了其他测试 / 有 lint 错。返回信号触发 BB007 重试（换策略 `template → llm → history_calibration`，最多 `FIX_RETRY_MAX` 次）。

6. **VerificationResult 数据结构**：
   - `passed: bool`——是否通过（Tier1 三关全过 / Tier2 轻量全过）。
   - `tier: int`——1 或 2（由调用方传入，本任务不重算 Tier）。
   - `failed_gate: str | None`——失败关卡名（`"repro_regression"` / `"existing_tests"` / `"static_check"` / `None`）。
   - `fail_category: str | None`——失败分类（`"root_cause_error"` / `"patch_error"` / `None`）。
   - `details: dict`——各关详细结果（per-gate pass/fail + error info + stdout/stderr 摘要）。
   - `overturn_signal: dict | None`——root_cause_error 时携带的推翻信号（供 BB004 `overturn_root_cause` 使用，含 `overturning_stage="regression"` + 复现序列 fail 证据）。
   - `retry_signal: dict | None`——patch_error 时携带的重试信号（供 BB007 换策略，含 fail 关卡 + error info + `attempt_no`）。

7. **复现序列回归比对逻辑**（BF002 `run_reproduce` 重放）：
   - 输入：原始复现脚本（`reproduce_script: list[dict]`）+ baseline StepOutcome 列表（`baseline_outcomes: list[StepOutcome]`，修复前跑的）。
   - 执行：调 `run_reproduce(client, script, ...)` 在修复后 worktree 上重跑。
   - 比对：逐 step 对齐 `StepOutcome.action`（必须一致，否则视为脚本不匹配）+ `expected_signal`（baseline 预期）vs 新执行的 `actual_signal`。
   - **root_cause_error 判定**：新执行结果中，baseline 原报 bug 的 step（`actual_signal` 含 crash/error 信号）在新执行中**仍报同样的 bug 信号**（`signal_type` + `pattern` 匹配）→ 根因未修复 → `fail_category="root_cause_error"`。
   - **通过判定**：新执行结果中，baseline 原报 bug 的 step 不再出现 crash/error 信号（`actual_signal` 为 None 或 severity 降级）→ 复现序列回归关通过。
   - **执行异常降级**：`run_reproduce` 抛异常（如模拟器连不上）→ 复现序列回归关 fail，`fail_category="patch_error"`（不能确定根因错，按补丁问题处理，让 BB007 重试或人工检查）。

8. **静态检查命令可配置**（`static_check_commands: list[str]`）：
   - 默认 `["ruff check .", "mypy ."]`（Python 项目默认）。
   - 通过构造函数参数或 config 注入，支持 Flutter 项目覆盖为 `["flutter analyze", "dart format --set-exit-if-changed ."]`。
   - 逐条执行（`subprocess.run(cmd, shell=True, capture_output=True)`），任一条 exit code != 0 → 静态检查关 fail。
   - 执行超时（默认 60s/条）→ 视为 fail。

9. **既有测试命令可配置**（`test_command: str` / `tier2_test_subset_command: str`）：
   - `test_command` 默认 `"pytest tests/"`（Tier1 全量测试）。
   - `tier2_test_subset_command` 默认 `"pytest tests/unit/"`（Tier2 测试子集）。
   - 通过构造函数参数或 config 注入。
   - exit code != 0 → 测试关 fail。

10. **Tier 分级由调用方传入**（本任务不重算 Tier）：
    - `verify(tier=1, ...)` → 执行三关全量。
    - `verify(tier=2, ...)` → 执行轻量验证（静态 + 子集测试）。
    - Tier 来自 BB006（ConfidenceScore.tier），Orchestrator 传入。

11. **单元测试**：`tests/unit/fix/test_regression_verifier.py`，全 mock（`run_reproduce` / `subprocess.run`），覆盖 Tier1 三关全过 / Tier1 各关 fail / Tier2 轻量通过 / Tier2 轻量 fail / fail 分类（root_cause_error / patch_error）/ 信号返回（overturn / retry）/ 配置覆盖 / 执行异常降级。

### 不做什么（OUT of scope）

- **不重算 Tier**：Tier 由 BB006 输出、Orchestrator 传入。本任务按传入的 tier 决定执行三关全量还是轻量验证。
- **不调 BB004 / BB007**：本任务返回 `VerificationResult` 信号（overturn_signal / retry_signal），由 Orchestrator 消费信号后决定调 BB004 `overturn_root_cause` 还是 BB007 重试。本任务不直接调 BB004 / BB007。
- **不持久化 VerificationResult**：返回内存对象，持久化（写入 `FixPatch.verification_report` / `BugReport.verification_report`）由调用方负责。
- **不实现 BB009 PR 提交**：验证通过后提 PR 由 BB009 负责。
- **不实现 BB007 自动修复**：patch_error 时的换策略重试由 BB007 负责，本任务只返回 retry_signal。
- **不实现模拟器管理**：模拟器启停 / APK 安装由 BF002 负责，本任务接收已连接的 `ADBClient` + 已应用的 patch worktree。
- **不做 async 接口**：所有方法为同步 `def`（subprocess 调用为同步阻塞）。
- **不生成复现脚本**：复现脚本由 BB003（PlaybookExecutor）产出，本任务直接 replay 已有脚本。

## 关键决策

### Q1：三关是否并行？

**决策：串行（短路，任一关 fail 即终止）。**

理由：
1. 三关有逻辑依赖：复现序列回归 fail（root_cause_error）时，跑既有测试和静态检查无意义——根因都错了，patch 质量检查是浪费。
2. 串行短路节省执行时间：复现序列回归最早（最可能因 root_cause_error 短路），静态检查最晚（最快、最便宜但因前两关已过才到）。
3. 并行引入复杂度（结果聚合 / 部分失败语义），且三关总执行时间在可接受范围（复现序列 ~30s + 测试 ~60s + 静态 ~10s），无需并行优化。

### Q2：复现序列回归如何比对？

**决策：StepOutcome.action + expected_signal 对齐，新执行结果与 baseline 比较。**

理由：
1. BF002 `run_reproduce` 返回 `list[StepOutcome]`，每步含 `action` / `expected_signal` / `actual_signal`。
2. baseline_outcomes（修复前跑的）中，原报 bug 的 step 特征是 `actual_signal` 非 None 且 severity 为 CRASH/ERROR。
3. 新执行（修复后重跑）中，对比同 step_no 位置：
   - 仍报同样信号（signal_type + pattern 匹配）→ bug 未修复 → root_cause_error。
   - 不再报信号（actual_signal=None 或 severity 降级）→ bug 已修复 → 复现序列回归关通过。
4. action 不一致时记录 warning 但不直接判 fail（脚本可能因 patch 微调了步骤参数），以信号比对为主要判据。
5. 不做截图像素级比对（成本高且 Flutter 自绘控件像素不稳定），以 logcat 信号比对为主。

### Q3：静态检查如何配置？

**决策：config 的 `static_check_commands: list[str]`（默认 `["ruff check .", "mypy ."]`）。**

理由：
1. 不同项目技术栈不同（Python / Flutter / Android 原生），静态检查命令必须可配置。
2. 默认值 `["ruff check .", "mypy ."]` 对齐项目当前 Python 栈（`requirements.txt` 已含 ruff + mypy）。
3. 通过构造函数参数注入，Orchestrator 初始化时从 config 读取传入；也可在测试中直接构造自定义命令。
4. 逐条执行（非一次性 `&&` 连接），便于定位是哪条命令 fail（details 中分别记录每条命令的 exit code / stdout / stderr）。
5. `subprocess.run(cmd, shell=True)` 执行——接受完整 shell 命令字符串（如 `flutter analyze`），灵活性最高。

### Q4：fail_category 判定逻辑？

**决策：复现序列仍报原 bug → root_cause_error；序列通过但静态/测试挂 → patch_error。**

理由：
1. backend 5.1 第 764-766 行明确分流：
   - "fail-根因错"（复现序列仍报原 bug）→ BB004 根因回退（`rootcause.overturned`）。
   - "fail-补丁问题"（序列通过但其他关挂）→ BB007 换策略重试（F4a）。
2. 语义区分：
   - root_cause_error：根因定位错了，修的不是真正的问题（或修了但没修对地方），复现序列中原 bug 信号仍然出现。需要回假设树重新下钻。
   - patch_error：根因方向对（bug 信号消失了），但 patch 有副作用（破坏其他测试 / lint 不通过）。需要在同根因下换 patch 策略重试。
3. run_reproduce 异常（模拟器连不上等）→ 不能确定根因错，按 patch_error 降级处理（让 BB007 重试或人工检查），避免误触发 BB004 根因回退（回退代价大）。
4. Tier2 无复现序列回归关 → 所有 fail 都是 patch_error（静态检查或测试子集 fail）。

### Q5：Tier 分级由谁决定？

**决策：调用方传入 tier（来自 BB006），本任务不重算。**

理由：
1. BB006（ConfidenceEvaluator）已实现 Tier 分级（三维打分 → Tier 1-4），BB008 不应重复计算。
2. Orchestrator 调 `verify(tier=bug_report.tier, ...)` 传入 Tier，BB008 按 tier 决定执行策略：
   - tier=1 → 三关全量。
   - tier=2 → 轻量验证。
3. tier=3/4 不进入 BB008（Orchestrator 分流到 BB010 缺口诊断），BB008 构造函数不需处理 tier=3/4。
4. 若传入 tier 不在 {1, 2} → 抛 `ValueError`（防御性，不静默降级）。

### retry_signal.next_strategy 推进逻辑

```python
_STRATEGY_CHAIN = ["template", "llm", "history_calibration"]

def _next_strategy(self, current_strategy: Optional[str], attempt_no: int) -> str:
    """根据当前策略和尝试号推荐下一策略。"""
    if current_strategy is None:
        return _STRATEGY_CHAIN[0]
    try:
        idx = _STRATEGY_CHAIN.index(current_strategy)
    except ValueError:
        return _STRATEGY_CHAIN[0]
    next_idx = min(idx + 1, len(_STRATEGY_CHAIN) - 1)
    return _STRATEGY_CHAIN[next_idx]
```

## 风险与降级

| 风险 | 影响 | 降级 |
|------|------|------|
| run_reproduce 抛异常（模拟器不可用） | 复现序列回归关无法执行 | 按 patch_error 降级（不误判 root_cause_error），retry_signal 携带异常信息 |
| subprocess 命令超时 | 静态检查/测试关卡住 | 超时阈值（60s/300s），超时视为 fail |
| subprocess 命令不存在（如 ruff 未安装） | 静态检查关报错 | 捕获异常，视为 fail，details 含错误信息 |
| baseline_outcomes 为空（无修复前复现记录） | 无法比对信号 | 复现序列回归关视为 pass（无 baseline 无法判定，降级为只跑测试+静态） |
| FIX_RETRY_MAX=0（配置不允许重试） | patch_error 时 should_retry 始终 False | retry_signal 正确返回 should_retry=False，Orchestrator 转缺口诊断 |
| 复现脚本 action 微调（baseline vs 新执行不一致） | 信号比对错位 | action 不一致记录 warning，以 step_no 对齐 + 信号比对为主判据 |
