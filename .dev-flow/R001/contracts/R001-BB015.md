## 任务边界

### 做什么（IN scope）

1. **新建 `agent/diagnosis/manual_fix_ingestor.py`**：ManualFixIngestor 类——抓取人工修复 commit patch → 引导填 root_cause/trigger_conditions → 写 KBEntry(pattern)。**唯一允许写 pattern 层的入口**（INV-3/AP-3），其他模块写 pattern 被拒。

2. **抓取人修 commit patch（`capture_fix_patch`）**：调 git_client.diff / git_client.diff_range 获取人工修复 commit 的 unified diff patch。patch 格式为标准 unified diff（`--- a/file` / `+++ b/file` / `@@ -line,line +line,line @@`），由 git_client 产出。

3. **引导填 root_cause/trigger_conditions（`collect_metadata`）**：接收结构化输入（由人工 API 填写），包含：
   - root_cause（必填）：人工判定的根因描述。
   - trigger_conditions（必填）：触发该 bug 的条件描述。
   - symptom_type（可选）：症状分类（如 "null_pointer" / "race_condition"）。
   - source_bug_id（必填）：对应的 BugReport id，用于追溯。

4. **写 KBEntry(pattern)（`_write_pattern`）**：调 `KBRetriever.add_pattern(patch_content, root_cause, trigger_conditions, symptom_type, source_bug_id)` 写入 pattern 层。这是**全系统唯一**调用 add_pattern 的地方。

5. **INV-3/AP-3 守护**：ManualFixIngestor 是唯一包含 `add_pattern` 调用的模块。其他模块（BB013 反思 agent 等）无 add_pattern 方法（BB013 Contract AC-4 已约束）。KBRetriever.add_pattern 可在内部加 source 校验（检查调用栈来源是否为 ManualFixIngestor），但本任务不负责 KBRetriever 内部实现——本任务的责任是从 BB015 侧保证唯一入口。

6. **PatternRecord dataclass**：录入记录结构——patch_content（unified diff 文本）/ root_cause / trigger_conditions / symptom_type / source_bug_id。

7. **校验（`_validate_input`）**：root_cause 和 trigger_conditions 必填，缺失抛 ValueError（附明确错误信息）。patch_content 不能为空（空 patch 无意义）。source_bug_id 必须有效（非空字符串）。

8. **去重检查（`_check_duplicate`）**：调 KBRetriever 查询是否已有相同 patch_content 的 pattern（避免同一修复重复录入）。已存在 → 返回 IngestResult(skipped=True, reason="duplicate_pattern")，不重复写入。

9. **单元测试**：`tests/unit/diagnosis/test_manual_fix_ingestor.py`，全 mock（git_client / KBRetriever），覆盖 patch 抓取 / 元数据校验 / pattern 写入 / INV-3 守护 / 去重 / 降级。

### 不做什么（OUT of scope）

- **不实现 git_client 基础设施**：git_client（git diff / git log 封装）由 INF 层提供，本任务通过依赖注入接收。不实现 git 命令执行 / 仓库遍历。
- **不实现人工交互 UI**：人工填写 root_cause/trigger_conditions 通过 API（FF01/FF02 后端入口）传入，本任务接收结构化输入，不做终端交互 / Web 表单。
- **不做 root_cause 语义校验**：root_cause 是人工填写的自然语言描述，本任务只校验非空，不校验语义正确性（人填的由人负责）。
- **不自动提取 pattern（不做 LLM）**：本任务不调 LLM 从 patch 自动推断 root_cause/trigger_conditions——这些由人工显式填写。自动提取是 BB013（反思 agent）的职责，且 BB013 写 negative_knowledge 不写 pattern。
- **不触发回流 / 不通知**：录入完成后不调 ReflowManager（BB011）或发通知。录入是终点动作（pattern 已入 KB，下次自动诊断可命中），无需后续编排。
- **不做 async 接口**：所有方法为同步 `def`（git diff + KB 写入均为同步操作）。

## 验收标准（可测试）

### AC-1：抓取人修 commit patch（git_client.diff/diff_range）

- **断言**：`capture_fix_patch(commit_sha)` 调 `git_client.diff(commit_sha)` 或 `git_client.diff_range(base_sha, head_sha)` 获取 unified diff。
- **断言**：返回的 patch_content 为标准 unified diff 格式（含 `--- a/` / `+++ b/` / `@@` hunk 标记）。
- **断言**：git_client=None（未注入）→ 抛 RuntimeError（"git_client not configured"），无法抓取 patch。
- **断言**：git_client.diff 抛异常（如 commit 不存在）→ 捕获 + 重新抛出为 PatchCaptureError（附原始错误信息）。

### AC-2：引导填 root_cause/trigger_conditions（接收结构化输入）

- **断言**：`collect_metadata(root_cause, trigger_conditions, symptom_type, source_bug_id)` 接收结构化参数。
- **断言**：root_cause 为空字符串或 None → 抛 ValueError（"root_cause is required"）。
- **断言**：trigger_conditions 为空字符串或 None → 抛 ValueError（"trigger_conditions is required"）。
- **断言**：source_bug_id 为空字符串或 None → 抛 ValueError（"source_bug_id is required"）。
- **断言**：symptom_type 为可选参数，未传时默认 None（不强制要求人工分类）。

### AC-3：写 KBEntry(pattern)（layer=pattern）

- **断言**：`_write_pattern(record)` 调 `kb_retriever.add_pattern(patch_content=..., root_cause=..., trigger_conditions=..., symptom_type=..., source_bug_id=...)`。
- **断言**：写入的 layer 为 pattern（由 KBRetriever.add_pattern 内部处理，本任务调正确的方法即保证）。
- **断言**：kb_retriever=None（未注入）→ 抛 RuntimeError（"kb_retriever not configured"），无法写入 pattern。
- **断言**：kb_retriever.add_pattern 抛异常 → 捕获 + 重新抛出为 PatternWriteError（附原始错误信息 + record 内容）。

### AC-4：INV-3/AP-3 守护（唯一允许写 pattern 层的入口）

### AC-5：PatternRecord dataclass

- **断言**：`PatternRecord` 为 `@dataclass`，字段：`patch_content: str` / `root_cause: str` / `trigger_conditions: str` / `symptom_type: Optional[str]` / `source_bug_id: str`。

- **断言**：可通过 `dataclasses.asdict()` 序列化为 dict（供日志 / 审计）。

### AC-6：校验（root_cause/trigger_conditions 必填，缺失抛 ValueError）

- **断言**：`_validate_input(record)` 对完整 PatternRecord（所有必填字段非空）→ 通过校验，无异常。

- **断言**：root_cause=None → 抛 ValueError。
- **断言**：trigger_conditions="" → 抛 ValueError。
- **断言**：trigger_conditions=None → 抛 ValueError。
- **断言**：patch_content="" → 抛 ValueError（"patch_content is empty"）。

### AC-7：去重检查（KB 已有相同 patch_content → 跳过 + 返回 skipped）

## 关键决策

### Q1：patch 格式？

**决策：unified diff（git_client 产出标准格式）。**

理由：
1. unified diff 是 git 的标准输出格式，git_client.diff / git_client.diff_range 直接产出。
2. unified diff 可读性强（人工可审阅）、可程序化解析（后续自动诊断可做 patch 匹配）。
3. patch_content 作为 pattern 的核心内容，存原始 unified diff 文本——不做归一化 / AST 解析（MVP 阶段精确文本匹配即可）。
4. 多文件修改：单个 commit 可能改多文件，unified diff 自然支持多文件 diff（连续 `diff --git` 块）。

### Q2：谁触发？

**决策：人工 API（FF01/FF02 后端入口）显式调用。**

理由：
1. pattern 层是高可信知识（"确定的修复模板"），必须人工确认后写入——不可自动触发。
2. FF01/FF02 提供 REST API，人工修复 bug 后在前端填写 root_cause/trigger_conditions + 选择 commit → API 调 ManualFixIngestor.ingest()。
3. 不做自动检测（如"监测到 commit → 自动提取 pattern"），避免噪声写入 pattern 层。
4. 与 BB013 的边界：BB013 在 ORB01 编排中自动调用（反思阶段），BB015 需人工显式触发——两者触发方式不同，知识可信度不同。

### Q3：与 BB013 边界？

**决策：BB013 写 negative_knowledge（自动），BB015 写 pattern（人工触发），互不重叠。**

理由：
1. BB013（反思 agent）：自动从 refuted 假设提取 negative_knowledge——记录"什么不该做"，可信度中等（LLM 提取），自动触发。
2. BB015（人工修复录入器）：人工从修复 commit 录入 pattern——记录"应该怎么修"，可信度高（人工确认），人工触发。
3. 两者写入的 KB 层不同（negative_knowledge vs pattern），调用的 KBRetriever 方法不同（add_negative_knowledge vs add_pattern），available_operations 完全不重叠。
4. INV-3 守护分工：BB013 无 add_pattern（Contract AC-4），BB015 有 add_pattern 且是唯一入口——从代码结构上形成单向约束。

### Q4：去重策略为什么用精确匹配？

**决策：基于 patch_content 精确文本匹配，不做模糊匹配 / 归一化。**

理由：
1. MVP 阶段精确匹配已足够——同一 commit 重复录入是最常见场景，精确匹配可拦截。
2. 模糊匹配（如忽略空白 / AST 级 diff 相似度）引入复杂性 + 误判风险，不适合 MVP。
3. 人工录入频率低（每次 bug 修复后一次），即使偶尔重复录入，pattern 层多一条相似条目不致命（BB004 negate_and_prune 会做相似度剪枝）。
4. 后续可升级去重策略（如 patch hash + 相似度阈值），但 MVP 保持简单。

### Q5：为什么不让 KBRetriever.add_pattern 做来源校验？

**决策：本任务从 BB015 侧保证唯一入口，不依赖 KBRetriever 内部做调用栈校验。**

理由：
1. 调用栈校验（inspect.caller）脆弱且性能差，不作为主守护手段。
2. 主守护：BB013 Contract 已约束无 add_pattern 调用（AC-4 + grep 验证），BB015 是唯一调用方——从模块边界保证。
3. 辅助守护：available_operations 白名单（BB013 和 BB015 各自的 Contract 均有断言），CI 持续验证。
4. 如果未来有新模块需要写 pattern，必须走 Contract 协商——新增模块的 Contract 必须明确 INV-3 审查，不可绕过。

## 实现要点

### 类设计

```python
from __future__ import annotations

from dataclasses import dataclass
from typing import Any, Optional
import logging

logger = logging.getLogger(__name__)


class PatchCaptureError(Exception):
    """Patch 抓取失败。"""


class PatternWriteError(Exception):
    """Pattern 写入失败。"""


@dataclass
class PatternRecord:
    """人工修复 pattern 录入记录。"""
    patch_content: str
    root_cause: str
    trigger_conditions: str
    symptom_type: Optional[str] = None
    source_bug_id: str = ""


@dataclass
class IngestResult:
    """录入结果。"""
    success: bool
    skipped: bool = False
    reason: Optional[str] = None
    pattern_id: Optional[str] = None
    record: Optional[PatternRecord] = None


class ManualFixIngestor:
    """人工修复录入器：人修 patch → KB pattern。

    INV-3/AP-3：唯一允许写 pattern 层的入口。
    """

    # INV-3/AP-3：唯一操作是 add_pattern
    AVAILABLE_OPERATIONS = frozenset({"add_pattern"})

    def __init__(
        self,
        *,
        git_client: Any,  # INF git_client（diff / diff_range）
        kb_retriever: Optional[Any] = None,  # BF005 KBRetriever
    ) -> None:
        self._git_client = git_client
        self._kb_retriever = kb_retriever

    @property
    def available_operations(self) -> list[str]:
        """返回可用写入操作（INV-3/AP-3：仅 add_pattern）。"""
        return sorted(self.AVAILABLE_OPERATIONS)

    def ingest(
        self,
        commit_sha: str,
        root_cause: str,
        trigger_conditions: str,
        source_bug_id: str,
        symptom_type: Optional[str] = None,
        base_sha: Optional[str] = None,
    ) -> IngestResult:
        """主入口：抓取 patch → 校验 → 去重 → 写 pattern。"""
        ...

    def capture_fix_patch(
        self,
        commit_sha: str,
        base_sha: Optional[str] = None,
    ) -> str:
        """抓取人修 commit 的 unified diff patch。"""
        ...

    def collect_metadata(
        self,
        root_cause: str,
        trigger_conditions: str,
        source_bug_id: str,
        symptom_type: Optional[str] = None,
    ) -> PatternRecord:
        """收集人工填写的元数据（结构化输入）。"""
        ...

    def _validate_input(self, record: PatternRecord) -> None:
        """校验必填字段（root_cause / trigger_conditions / patch_content / source_bug_id）。"""
        ...

    def _check_duplicate(self, patch_content: str) -> bool:
        """去重检查：KB 已有相同 patch_content → True。"""
        ...

    def _write_pattern(self, record: PatternRecord) -> str:
        """写 KBEntry(pattern)——全系统唯一 add_pattern 调用入口。"""
        ...

    # INV-3 守护：显式不提供 add_negative_knowledge / add_raw_trajectory
    # 这些是 BB013 的职责，BB015 专注 pattern 层
```

### 录入流程

```
1. capture_fix_patch(commit_sha) → patch_content (unified diff)
2. collect_metadata(root_cause, trigger_conditions, ...) → PatternRecord
3. _validate_input(record) → 通过 / 抛 ValueError
4. _check_duplicate(patch_content) → True(跳过) / False(继续)
5. _write_pattern(record) → pattern_id
6. 返回 IngestResult(success=True, pattern_id=..., record=...)
```

| git_client 未注入或仓库不可用 | 无法抓取 patch | 抛 RuntimeError/PatchCaptureError，人工 API 返回错误提示 |
| 人工填写 root_cause 质量低（描述不准确） | pattern 匹配精度下降 | 本任务不做语义校验（人工填的由人负责）；symptom_type 可辅助分类 |
| 去重查询失败（KB 服务不可用） | 可能重复录入 | 降级为不去重（继续写入 + warning），宁可重复也不阻断人工录入 |
| patch 过大（改文件过多 / 行数过多） | KB 存储压力 + 匹配性能下降 | MVP 不做 patch 大小限制；后续可加 patch 截断 / 分片策略 |
| INV-3 被绕过（新模块误加 add_pattern） | pattern 层被非授权写入 | Contract 协商流程 + CI grep 验证 + available_operations 白名单测试 |
