## 任务边界

### 做什么（IN scope）
1. 新建 `agent/kb/` 包，落地三层 KB 存储 + 两阶段检索 + 陈旧降权 + 负向知识反查。
2. **三层 store**（共表 `kb_entries`，按 `layer` 字段区分，复用 SCH01 `KBEntry`）：
   - `TrajectoryStore`（`raw_trajectory` 层）：轨迹/假设的 CRUD
   - `NegativeKnowledgeStore`（`negative_knowledge` 层）：负向知识（refuted 假设）的 CRUD
   - `PatternStore`（`pattern` 层）：修复模式的 CRUD + **写入权限校验**（仅 `caller_id="bb015_manual_fix_recorder"` 白名单）
3. **KBRetriever**（`agent/kb/retriever.py`）：两阶段检索（symptom_type + layer 预过滤 → pgvector 排序）；stale ×0.5 降权；conflicting 成组返回；冷启动 degraded 判定。
4. **StalenessChecker**（`agent/kb/staleness_checker.py`）：检测 `git_commit_anchor` 与当前 HEAD 的差异 → revalidate → 失败标 `stale`（不删数据）。
5. **负向知识反查**（BF005.4）：放在 `agent/kb/retriever.py` 内的 `negate_hypotheses()` 方法（不单独建 negative_lookup.py），三档判定（prune / demote / unaffected）。
6. 自定义异常 `KBPermissionError`（`agent/kb/exceptions.py`）。
7. 单元测试 + 集成测试（Testcontainers pgvector/pgvector:pg16，沿用 INF03 conftest）。

### 不做什么（OUT of scope）
- **不改 SCH01 `kb_entry.py` 的字段名/类型**（`KBEntry` 已定义 layer / symptom_type / root_cause_signals / git_commit_anchor / validity_status / conflicting_entry_ids / source 等字段，本任务直接消费）。如需补充字段，需回 SCH01 协商，不在此 task 私改。
- **不实现 embedding 生成**：`root_cause_signals` 向量由调用方（BB004/BB013/BB015）传入；BF005 只负责存储与 pgvector 检索，不集成 embedding 模型。
- **不实现 git 差异计算**：StalenessChecker 的 git 距离判定接受外部传入的 `current_head` 与可选的 `commit_distance_fn`（默认实现为"commit 是否在当前分支历史中"），不在此 task 内调 `git` 子进程拉 HEAD（由调用方/BB013 反思 agent 提供 HEAD）。
- **不实现冲突自动发现**：`conflicting` 关系由写入方（PatternStore / 反思 agent）显式维护 `conflicting_entry_ids`；BF005 不做"自动识别两个条目冲突"的算法。
- **不做 aggregated 层 store**（design 第 913 行预留给 BB014，BF005 只覆盖 raw_trajectory / negative_knowledge / pattern 三层）。
- **不做 KB 写入的 LLM 抽取**（BB013 反思 / BB015 人工录入各自负责内容生成；store 只做持久化）。
- **不做跨 bug 聚合**（BB014 负责）。
- **不做 async 接口**（同步 SQLAlchemy Session，与 INF03 风格一致）。

### AC-1：三层 store CRUD（共表 layer 分流）
- **断言**：`TrajectoryStore.create(entry_dict)` 写入后 `layer == "raw_trajectory"`，DB 中可查到；`get(entry_id)` 返回该条目。
- **断言**：`NegativeKnowledgeStore.create()` 写入后 `layer == "negative_knowledge"`；`list(symptom_type="crash")` 按症状过滤正确。
- **断言**：`PatternStore.create()` 写入后 `layer == "pattern"` 且 `content` 含 `trigger_conditions / patch_template / fix_example`（pattern 层契约字段，调用方负责填）。
- **断言**：三层均支持 `update(entry_id, patch_dict)` / `delete(entry_id)`；delete 为硬删（KB 软删由 `validity_status` 字段承担，不靠 delete 标记）。
- **断言**：store 不串层——`TrajectoryStore.create()` 强制 `layer=raw_trajectory`，即使调用方传入 `layer="pattern"` 也被覆盖（避免误写）。

### AC-2：pattern_store 写入权限校验（INV-3 / AP-3）

- **接口**：`PatternStore.create(caller_id: str, entry_dict: dict)` / `update(caller_id: str, ...)`；`caller_id` 必传。
- **白名单**：`{"bb015_manual_fix_recorder"}`（常量 `PATTERN_WRITE_ALLOWLIST`）。
- **断言**：`caller_id="bb015_manual_fix_recorder"` → 写入成功。
- **断言**：`caller_id="bb013_reflection_agent"` 或任意非白名单值 → 抛 `KBPermissionError`，错误信息含 `caller_id` 与允许列表；DB 无写入（事务回滚）。
- **断言**：`TrajectoryStore` / `NegativeKnowledgeStore` 不做 caller_id 校验（这两层写入权限留给后续 task 约束，本 task 只锁 pattern 层）。
- **read 不校验**：`PatternStore.get/list` 不需要 caller_id（读权限不在此 task 约束）。

### AC-3：KBRetriever 两阶段检索算法（design 5.3）
- **输入**：`retrieve(symptom_type: str, root_cause_query_vector: list[float], layer: KBLayer, top_k: int = 5) -> RetrievalResult`。
- **阶段 1（预过滤 SQL）**：
  ```sql
  WHERE symptom_type = :symptom_type
    AND layer = :layer
    AND validity_status != 'archived'   -- KBEntry 无 archived，实际为 != 'deleted'；当前 schema 三态均保留
  ```
  实际：当前 `KBValidityStatus` 只有 valid/stale/conflicting，无 archived；预过滤只做 `symptom_type + layer`，validity 过滤交给阶段 2 降权逻辑。
- **阶段 2（pgvector 排序）**：
  ```sql
  ORDER BY root_cause_signals <-> :query_vector
  LIMIT :top_k
  ```
  使用余弦距离 `<=>` 或 L2 `<->`（pgvector 默认 opclass 支持，BF005 选 `<=>` 余弦距离，与"相似度"语义一致；距离 = 1 - 余弦相似度，retriever 内部转换）。
- **输出结构**：
  ```python
  @dataclass
  class RetrievedEntry:
      entry: KBEntry
      similarity: float          # 已应用 stale 降权后的最终相似度
      raw_similarity: float      # 原始相似度（降权前）
      validity_status: KBValidityStatus
      conflicting_with: list[str] | None  # conflicting 时附关联 entry_ids

  @dataclass
  class RetrievalResult:
      entries: list[RetrievedEntry]
      degraded: bool
  ```
- **断言**：候选集 > 0 且 top1 `raw_similarity >= KB_SIMILARITY_FLOOR(0.5)` → 返回 top_k 条，`degraded=False`。
- **断言**：检索结果按 `similarity`（降权后）降序排列。
- **断言**：`symptom_type` 不匹配的条目不出现在结果中（预过滤生效）。
- **断言**：`layer` 不匹配的条目不出现（跨层隔离）。

### AC-4：staleness 降权（D5 / 盲点 1）
- **降权规则**：`validity_status == "stale"` 的条目，`similarity = raw_similarity * KB_STALE_DEMOTE(0.5)`；保留在结果中（不剔除）。
- **断言**：一条 stale 条目 `raw_similarity=0.8` → 输出 `similarity=0.4`，`raw_similarity=0.8`，`validity_status="stale"`。
- **断言**：stale 条目与 valid 条目同时存在时，排序按降权后 similarity（stale 可能排到 valid 之后）。
- **断言**：stale 标记由 StalenessChecker 写入 `validity_status`（AC-6），retriever 只读不写。

### AC-5：conflicting 成组返回（D9 / 盲点 5）
- **决策**：conflicting 关系**显式**维护（`KBEntry.conflicting_entry_ids: list[str]`，由写入方填），retriever 不自动发现冲突。
- **返回规则**：当返回的某条目 `validity_status == "conflicting"` 时，`conflicting_with` 字段填充其 `conflicting_entry_ids`（list of entry_id），调用方决策；非 conflicting 条目 `conflicting_with=None`。
- **断言**：DB 中 entry A `validity_status=conflicting` + `conflicting_entry_ids=["B","C"]`，检索命中 A → `RetrievedEntry.conflicting_with == ["B","C"]`。
- **断言**：conflicting 条目**不自动降权**（与 stale 不同，conflicting 由调用方决策是否采纳，retriever 原样返回相似度）。
- **断言**：若 `conflicting_entry_ids` 中的条目不在本次 top_k 结果内，仍只在 `conflicting_with` 字段附 id 列表（不强制拉取关联条目入结果，避免结果膨胀）。

### AC-6：StalenessChecker（D5）
- **接口**：`check_and_mark(entries: list[KBEntry], current_head: str, commit_distance_fn: Callable[[str, str], int] | None = None) -> list[str]`（返回被标记为 stale 的 entry_ids）。
- **差异判定（默认）**：`commit_distance_fn(entry.git_commit_anchor, current_head)` 返回距离；默认实现为"anchor 是否在 current_head 的祖先链中"——**不在祖先链 → 距离 = ∞ → 标 stale**；在祖先链 → 距离 = 0 → 保持原状。可选注入自定义 distance_fn（如按 commit count 阈值 100）。
- **决策**：MVP 采用"祖先链归属"判定（简单 + 不依赖 git 子进程拉 log）；commit count 阈值方案作为可注入策略预留，不在默认路径实现。
- **revalidate 钩子**：`check_and_mark` 接受可选 `revalidate_fn(entry) -> bool`；若提供，差异判定为"漂移"后调 revalidate_fn，返回 False 才最终标 stale（返回 True 表示内容仍有效，不标 stale）。MVP 默认 `revalidate_fn=None` → 差异即标 stale（保守策略）。
- **标 stale 操作**：`update validity_status='stale', last_revalidated_at=now()`；**不删 root_cause_signals / content**（软标，保留审计）。
- **断言**：entry.git_commit_anchor 在 current_head 祖先链 → 不标 stale。
- **断言**：entry.git_commit_anchor 不在祖先链（分支已分叉 / commit 被 rebase 掉）→ 标 stale，DB 中 `validity_status='stale'`，`last_revalidated_at` 更新。
- **断言**：`git_commit_anchor IS NULL` 的条目 → 不标 stale（无 anchor 无法判定，保守不标；这类条目通常是 negative_knowledge 层，与代码版本无关）。
- **断言**：注入 `revalidate_fn` 返回 True → 即使差异判定为漂移，也不标 stale。

### AC-7：冷启动降级（degraded）
- **决策**：采用"`candidate_pool < KB_COLD_START_N OR top1_raw_similarity < KB_SIMILARITY_FLOOR → degraded=True`"复合判定。
- **判定逻辑**：
  - candidate_pool = 阶段 1 预过滤后的候选总数（validity 三态都算）
  - `degraded = (candidate_pool < KB_COLD_START_N=10) OR (top1_raw_similarity < KB_SIMILARITY_FLOOR=0.5)`
  - 当候选池为空（candidate_pool=0）→ degraded=True，entries=[]
- **断言**：candidate_pool=3（< 10）→ degraded=True，即使 top1_similarity=0.9（冷启动期，结果可用但提示调用方走降级路径）。
- **断言**：candidate_pool=15，top1_raw_similarity=0.3（< 0.5）→ degraded=True，entries 仍返回（调用方决定是否丢弃）。
- **断言**：candidate_pool=15，top1_raw_similarity=0.7 → degraded=False。
- **注**：`raw_similarity` 比较用降权前的值（冷启动判定关注"有无有效模式"，stale 降权不应误导冷启动判定）。

### AC-8：负向知识反查（BF005.4，三档）
- **接口**：`KBRetriever.negate_hypotheses(hypotheses: list[HypothesisInput], symptom_type: str) -> list[NegativeVerdict]`（放在 retriever.py，不单独建文件）。
- **HypothesisInput**：`{hypothesis_id: str, root_cause_vector: list[float]}`（调用方 BB004 负责向量化）。
- **流程**：对每个假设，检索 `layer=negative_knowledge + symptom_type` 层，取 top1 相似度（余弦）。
- **NegativeVerdict**：
  ```python
  @dataclass
  class NegativeVerdict:
      hypothesis_id: str
      max_negative_similarity: float | None  # 无匹配时 None
      prune: bool                  # similarity > KB_NEGATIVE_PRUNE(0.85)
      demote_factor: float         # 0.6<=sim<=0.85 → 0.3；其他 → 1.0（不影响）
  ```
- **三档**：
  - `similarity > KB_NEGATIVE_PRUNE(0.85)` → `prune=True, demote_factor=1.0`（剪枝，调用方丢弃假设）
  - `KB_NEGATIVE_DEMOTE(0.6) <= similarity <= 0.85` → `prune=False, demote_factor=0.3`（降权 ×0.3）
  - `similarity < 0.6` 或无匹配 → `prune=False, demote_factor=1.0`（不影响）
- **断言**：sim=0.9 → prune=True。
- **断言**：sim=0.7 → prune=False, demote_factor=0.3。
- **断言**：sim=0.4 → prune=False, demote_factor=1.0。
- **断言**：negative_knowledge 层无该 symptom_type 的条目 → max_negative_similarity=None, prune=False, demote_factor=1.0。

## 风险与降级
| 风险 | 影响 | 降级方案 |
|------|------|----------|
| pgvector `<=>` opclass 未建索引 | 大表检索慢 | MVP 数据量小（冷启动期），全表扫可接受；后续 task 加 `CREATE INDEX USING hnsw` |
| embedding 维度与 pgvector 列维度不一致 | 写入/检索失败 | BF005 不生成向量，由调用方保证维度一致；store 层不做 dim 校验（pgvector 可变长 Vector()） |
| conflicting_entry_ids 指向已删除条目 | conflicting_with 出现悬空 id | MVP 不处理（硬删罕见；调用方读时容错）；后续可加级联或软删 |
| StalenessChecker 误标 stale（祖先链判定过严） | 有效模式被降权 | 提供 `revalidate_fn` 钩子让调用方覆核；MVP 默认无钩子时差异即标 stale，保守优先 |
| 负向知识反查把有效假设误剪枝 | BB004 丢失候选假设 | 阈值 0.85 偏高（只在强匹配才剪枝）；demote 档保留假设仅降权；参数化在 config 可调 |

## 实现要点
1. **共表 layer 分流**：三层 store 操作同一张 `kb_entries` 表，差异只在 `layer` 字段。store 在 create 时强制覆写 `layer`，避免调用方误传。
2. **caller_id 显式传参**：不用 contextvar / threading.local（隐式上下文难测 + 跨线程不可靠）；PatternStore 写方法签名显式带 `caller_id`。
3. **KBPermissionError**：继承 `Exception`（不继承 PermissionError 内置，避免被上层宽泛 except 吞掉）；放在 `agent/kb/exceptions.py`。
4. **pgvector 距离选择**：用余弦距离 `<=>`（`root_cause_signals` 语义为"方向相似"，余弦比 L2 合适）；距离转相似度 `sim = 1 - distance`。
5. **stale 降权只改输出不改 DB**：retriever 计算 `similarity = raw * 0.5` 只影响排序与返回值，不写回 DB（DB 中 validity_status 已是 stale，降权是检索期行为）。
6. **degraded 用 raw_similarity 判定**：冷启动判定关注"有无有效模式"，用降权前相似度避免 stale 条目把 degraded 拉高。
7. **negate_hypotheses 放 retriever.py**：避免文件爆炸；负向反查本质是 negative_knowledge 层的检索 + 三档分类，与 retriever 同源。
8. **StalenessChecker 不调 git 子进程**：`current_head` 与 `commit_distance_fn` 由调用方注入（BB013 反思 agent 在 revalidate 流程中提供 HEAD）；保持 BF005 无外部进程依赖。
9. **KBEntry 不加新字段**：所有逻辑用现有字段（layer / symptom_type / root_cause_signals / git_commit_anchor / validity_status / conflicting_entry_ids / source / last_revalidated_at）。
