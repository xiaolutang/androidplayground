# 🧠 JVM 内存模型与 Android 内存优化全指南

本篇从底层物理区域（Runtime Areas）、并发协议（JMM）到 Android 线上 OOM 治理进行全维度拆解。

---

## ⚔️ 第一阶段：JVM 运行时内存区域 (Runtime Data Areas)

这是物理层面数据存放的规则，解决的是“数据放在哪”的问题。

1.  **程序计数器 (PC Register)**：**线程私有**。记录当前线程执行指令的行号。唯一不会 OOM 的区域。
2.  **虚拟机栈 (Java Stack)**：**线程私有**。主管 Java 方法运行，内部是栈帧（局部变量表、操作数栈）。
3.  **本地方法栈 (Native Stack)**：**线程私有**。为 Native 方法服务。
4.  **堆 (Heap)**：**所有线程共享**。对象实例存放地，GC 主战场。
5.  **方法区 / 元空间 (Metaspace)**：**所有线程共享**。存类信息、常量、静态变量。Java 8 以后移至本地内存。

---

## ⚔️ 第二阶段：JMM (Java Memory Model)

这是逻辑层面的并发协议，解决的是“多线程如何安全通信”的问题。

### Q1: JMM 的三大特性是什么？
1.  **原子性 (Atomicity)**：操作不可分割。`synchronized` 保证原子性。
2.  **可见性 (Visibility)**：线程修改后其他线程立刻可见。`volatile` 强制从主内存读写。
3.  **有序性 (Ordering)**：禁止指令重排。`volatile` 引入内存屏障。

### Q2: 为什么 DCL 单例必须加 `volatile`？（必考压轴）
*   **现象**：`new Singleton()` 并非原子操作（分配 -> 构造 -> 指向）。
*   **风险**：指令重排可能导致“指向”先于“构造”。
*   **后果**：处于锁外面的线程可能拿到一个**还没执行构造函数的“半成品”对象**，从而引发空指针或崩溃。
*   **结论**：`synchronized` 只保证锁内有序，不保证锁外观察到的顺序。必须加 `volatile` 铁腕禁止重排。

---

## ⚔️ 第三阶段：Android 内存泄漏与 OOM 治理

### 1. 内存泄漏本质
*   **GC Root 理论**：如果对象到 **Thread**、**Static** 或 **JNI** 等根节点有可达路径，则无法回收。
*   **重灾区**：Handler（非静态内部类持有 Activity）、单例长久引用、未取消的协程/匿名内部类。

### 2. OOM 的离奇死法
*   **FD 溢出**：文件句柄/Socket 超过 1024 限制。
*   **VSS 耗尽**：线程开太多导致虚拟地址空间（栈内存）爆掉。
*   **碎片化**：总内存够但没有连续的大块空间分配给大图。

### 3. 治理招式
*   **Bitmap 演进**：8.0 之后移至 Native 堆，靠 Cleaner 机制自动回收。
*   **线上监控**：利用 KOOM/OOMAnalyzer 进行 HPROF 裁剪上传。
*   **主动退避**：监听 `onTrimMemory` 级别，主动释放图片和单例缓存。
